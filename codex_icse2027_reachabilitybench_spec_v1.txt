Core paper positioning
======================

The paper has a dual positioning:

1. Benchmark contribution:
   ReachabilityBench is a controlled Java benchmark for evaluating whether LLMs can answer and explain method-reachability questions under exact oracle supervision.

2. Analytical/critical contribution:
   The benchmark tests a simple, elementary structural reasoning capability. The paper should show where LLMs succeed or fail on this controlled capability, and how failures depend on task family, structural difficulty, code-surface factors, and reasoning budget.

Tone toward existing benchmarks
-------------------------------
Use a complementary tone, not an aggressive one.

The paper should not claim that existing realistic code benchmarks are flawed or obsolete. Instead, it should argue that macroscopic benchmarks and controlled diagnostic benchmarks answer different questions.

Recommended wording:
"Existing code benchmarks are valuable for measuring end-to-end performance on realistic tasks. ReachabilityBench is complementary: it isolates a lower-level structural capability that may be hidden inside broader software-engineering tasks."

Reachability as an elementary capability
----------------------------------------
Reachability should be framed as an elementary program-understanding task.

It may be required as one component of larger SE tasks such as:
- bug fixing;
- code generation;
- debugging;
- impact analysis;
- security reachability analysis;
- repository-level issue resolution.

But do not claim that these larger tasks always require reachability, or that they reduce to reachability.

Recommended wording:
"Reachability is not presented as a complete model of software-engineering reasoning. Rather, it is an elementary structural capability that can be involved in more complex tasks. Larger tasks may require a model to determine whether one method can directly or indirectly reach another, but reachability is only one component among many."

Terminology
===========

Use the following main terms.

Benchmark name
--------------
ReachabilityBench.

Task families
-------------
1. Control-flow reachability.
2. Condition-aware reachability.

Important terminology decision
------------------------------
Do not use "data-flow reachability" as the main term in the final paper.

At the beginning, the paper may mention that condition-aware reachability is a data-dependent extension of control-flow reachability, but after this clarification use "condition-aware reachability" as the main term.

Recommended wording:
"We use the term condition-aware reachability for the data-dependent extension of the task. Unlike full data-flow analysis, this setting does not aim to model arbitrary def-use relations, reaching definitions, or taint propagation. Instead, it keeps the same method-reachability question while allowing method calls to be guarded by conditions over generated variables and parameters."

Control-flow reachability
-------------------------
In control-flow reachability:
- method calls are placed outside control-flow structures;
- calls are not guarded by if, for, while, or other control-flow constructs;
- every generated method call is active for reachability;
- variables, comments, loops, and other code-surface elements may exist only if they do not affect method-call reachability.

Condition-aware reachability
----------------------------
In condition-aware reachability:
- the reachability question remains the same;
- method calls may remain outside control-flow structures or appear inside if statements;
- method calls are not guarded by loops in the final definition;
- calls inside if branches whose conditions evaluate to false are visible in the source code but are not executable;
- the model must distinguish syntactic call presence from executable reachability.

Syntactic vs executable call graph
----------------------------------
For condition-aware reachability, explicitly distinguish:

1. Syntactic call graph:
   Contains all method calls visible in the source code, including calls inside non-passing if branches.

2. Executable call graph:
   Contains only calls that are actually executed under the generated variable values and if conditions.

Calls inside false if branches:
- are distractors;
- belong to the syntactic call graph;
- do not belong to the executable call graph;
- are excluded from the oracle trace and reachability label.

Recommended wording:
"Condition-aware reachability separates syntactic call presence from executable reachability. A guarded call may appear in the Java source code but be placed inside an if branch whose condition evaluates to false. Such a call belongs to the syntactic call graph but not to the executable call graph used by the oracle."

Syntactic-call bias
-------------------
Use the term "syntactic-call bias" for a model error where the model treats the presence of a method call in the source code as evidence of reachability, even though the call is inside a non-executed branch and is absent from the executable call graph.

This term should appear in the Error Analysis section.

Benchmark structure
===================

Graph structure
---------------
The final ICSE paper should focus only on tree-shaped call graphs generated from randomized pseudo-binary trees.

Use this phrase:
"tree-shaped call graphs generated from randomized pseudo-binary trees"

Do not present linear call graphs as part of the evaluated benchmark.

Remove the "Linear Structure" subsection from the main paper.
If the codebase still supports linear generation, it may be mentioned only in artifact documentation or appendix, not as a main benchmark component.

Graph properties
----------------
- Nodes correspond to Java methods.
- Directed edges correspond to method calls.
- Generated graphs are acyclic.
- There are no cycles.
- There is no recursion.
- The structure is a randomized pseudo-binary tree.
- The current benchmark does not include inheritance, interfaces, dynamic dispatch, overloading, exceptions, recursion, external libraries, or multi-class projects.

Generated Java programs
-----------------------
Each benchmark instance is materialized as:
- a single Java class;
- containing many generated methods;
- methods call each other according to the generated tree-shaped call graph.

Do not imply that the benchmark currently tests:
- real repositories;
- multi-file projects;
- class hierarchies;
- polymorphism;
- dynamic dispatch;
- recursive/cyclic call graphs.

Method order shuffling
----------------------
Keep method order shuffling as a core design choice.

The generator preserves child/call order inside each method body, which defines the canonical traversal, but it shuffles the order of method declarations in the Java class.

Purpose:
- prevent models from exploiting declaration order;
- force models to reconstruct reachability from actual call relations.

Do not treat method order shuffling as an experimental ablation.

Canonical traversal and distance
================================

Canonical execution-oriented trace
----------------------------------
The oracle trace is defined as a canonical execution-oriented traversal trace, not necessarily the shortest path.

Important:
- Avoid saying simply "DFS" as the conceptual definition.
- DFS may be an implementation analogy, but the paper should defend the concept as execution-oriented traversal.

Definition:
The canonical traversal is graph-defined and code-aligned.

The generator:
1. creates an ordered tree-shaped call graph;
2. materializes the order of children as the textual order of call statements inside each Java method body.

Therefore, the oracle traversal follows:
- the ordered call graph;
- the order in which calls appear in the generated Java code.

Recommended wording:
"The canonical execution-oriented order is defined by the ordered tree generated by the benchmark. When the abstract graph is materialized as Java code, the generator preserves this child order as the textual order of method calls inside each generated method body. Therefore, the oracle traversal is both graph-defined and code-aligned."

Positive cases
--------------
For positive queries:
- the final answer is True;
- the trace corresponds to the first execution-consistent exploration that reaches the target;
- the trace follows method calls in the canonical execution-oriented order;
- it is not necessarily the shortest source-target path.

Negative cases
--------------
For negative queries:
- the final answer is False;
- the trace corresponds to the canonical execution-oriented exploration from the source until the reachable region has been exhausted without reaching the target.

Condition-aware traces
----------------------
For condition-aware instances:
- the canonical trace follows the executable call graph;
- calls in false if branches are excluded from the canonical trace;
- syntactic-but-non-executable calls may be discussed as distractors in the error analysis.

Distance
--------
The main distance used in the paper is:
canonical execution-trace distance.

It is not the shortest-path distance in the abstract graph.

Definition:
- For positive queries, distance is the number of execution-consistent traversal steps required to reach the target from the source.
- For negative queries, distance is defined over the canonical exploration performed from the source before concluding that the target is unreachable.
- Distances are signed:
  +d for positive/reachable queries;
  -d for negative/unreachable queries.

Use "absolute canonical distance" or "target distance level" for d in {1, ..., 25}.
Use "signed canonical distance" for +d and -d.

Metrics
=======

Main metrics
------------
Use the following main metrics in this order:

1. Final-answer accuracy
2. Canonical execution-trace accuracy
3. Trace completeness
4. Graph-valid exploration accuracy
5. NO_RESPONSE rate

Main table should report strict scores only:
NO_RESPONSE = incorrect.

Full tables in the appendix should report:
- strict scores;
- conditional scores excluding NO_RESPONSE from the denominator;
- NO_RESPONSE rate.

Final-answer accuracy
---------------------
Measures whether the model gives the correct True/False answer.

Primary convention:
NO_RESPONSE = incorrect.

Secondary convention:
Exclude NO_RESPONSE from denominator.

Canonical execution-trace accuracy
----------------------------------
Measures whether the predicted trace exactly matches the canonical execution-oriented trace.

This is the main trace metric.

Trace completeness
------------------
Measures the fraction of the canonical execution trace recovered in order by the model.

Keep this as a main metric because exact trace match is strict and partial traces are informative.

Graph-valid exploration accuracy
--------------------------------
Measures whether the predicted trace is structurally valid with respect to the generated call graph, even if it does not match the canonical order exactly.

Definition:
Starting from the source method, the evaluator maintains the set of methods already visited. Each next predicted method is accepted if it is directly callable from at least one method already in the visited set.

Positive queries:
- predicted exploration must be graph-valid;
- must reach/end at the target.

Negative queries:
- predicted exploration must be graph-valid;
- must cover the reachable region from the source without reaching the target.

Place this metric after canonical trace metrics because it is a relaxed structural-validity metric.

NO_RESPONSE rate
----------------
NO_RESPONSE includes cases where:
- no final_answer can be extracted;
- no valid JSON can be parsed;
- the output is truncated before producing the required structured answer;
- the model does not follow the output schema.

Be careful:
NO_RESPONSE often corresponds to budget exhaustion/truncation, but do not claim it always does.

Strict vs conditional scores
----------------------------
For every main metric:
- strict score: NO_RESPONSE = false/incorrect;
- conditional score: NO_RESPONSE excluded.

Main paper:
- compact strict metrics only;
- include NO_RESPONSE rate.

Appendix:
- complete table with strict and conditional variants.

Secondary / appendix metrics
----------------------------
Move these to appendix or secondary analyses:
- shortest-chain accuracy / direct-chain accuracy;
- chain recall;
- trace recall;
- path recall;
- chain_gap;
- trace_gap;
- path_gap;
- emitted reasoning length.

Shortest-chain accuracy
-----------------------
Do not make shortest-chain accuracy central.

It is useful only as a secondary diagnostic because it measures whether the model produced the shortest source-target chain rather than the benchmark’s execution-oriented trace.

Reasoning models:

Non-reasoning models:

Baselines
=========

Do not include static or heuristic baselines in the final paper.

Reason:
A deterministic program-analysis algorithm can solve the generated reachability task by construction. The scientific question is not whether a graph traversal algorithm can solve reachability, but whether LLMs can reconstruct and explain it from generated Java code.

Replace baseline discussion with:
- exact oracle;
- dynamic/oracle validation pipeline;
- dataset sanity checks.

Recommended wording:
"We do not include traditional program-analysis baselines as competing methods. The benchmark is generated with an exact oracle, and deterministic graph traversal over the generated call structure would solve the task by construction. Our goal is instead to evaluate whether LLMs can recover and explain this structure from generated Java code. We therefore use programmatic analysis tools only for oracle validation and dataset sanity checks, not as baseline models."

Oracle validation
=================

Add a subsection in Benchmark Design:
"Oracle Validation"

Also add a short reminder in Methodology.

Validation checks
-----------------
The validation pipeline checks:

1. The generated Java code compiles.
2. The materialized methods and calls match the intended graph.
3. Positive questions are truly reachable.
4. Negative questions are truly unreachable.
5. Oracle traces correspond to the canonical execution-oriented traversal.
6. For condition-aware instances, generated variables and if conditions correctly determine whether guarded calls are executed.

Recommended wording:
"We validate generated instances using a programmatic oracle-validation pipeline. This pipeline checks that the generated Java code compiles, that the materialized method calls match the intended tree-shaped call graph, and that sampled positive and negative queries agree with the reachability relation induced by the generated program. It also validates that oracle traces follow the benchmark’s canonical execution-oriented traversal. For condition-aware instances, the validation additionally checks that generated variables and conditions correctly determine whether guarded calls are executed."

Prompt status
-------------
The final prompt was calibrated using preliminary experiments.

Pilot experiments were used to:
- make sure models understand the task;
- make sure models produce valid JSON;
- avoid under-specified prompts that produce bad performance due to misunderstanding;
- avoid over-specified prompts that tell models to use DFS, BFS, or another named traversal algorithm.

The final experiments will be rerun from scratch using the stabilized prompt.

Prompt placement
----------------
Main paper:

Appendix:

Prompt convention
-----------------
The prompt must define the trace as an explored call sequence, not as the shortest path.

The prompt should tell the model to:
- follow method calls in the order they appear in the code;
- start from the caller;
- continue until the target is reached or no further reachable calls remain.

Do not tell the model:
- "use DFS";
- "use BFS".

Control-flow prompt
-------------------
For control-flow:
- remove "executable";
- remove "data-flow reasoning";
- do not mention condition evaluation.

Condition-aware prompt
----------------------
For condition-aware:
- keep the notion of real executable reachability;
- replace "data-flow reasoning" with wording about conditions and variable values;
- say the model must account for conditions and variable values that determine whether guarded calls are executed.

Illustrative example
--------------------
Keep the illustrative example where the expected trace is:
["A", "B", "C", "D", "E"]

This example is useful because it clarifies that the trace is the explored call sequence in code order, not the shortest path such as ["A", "C", "E"].

Recommended wording:
"The prompt includes a small illustrative example to define the output schema and the expected trace convention. In particular, the example shows that traces should list the explored call sequence in code order, rather than only the shortest source-target chain. - comments;
- local variables;
- loops;
- if statements;

Discussion and limitations
==========================

Synthetic Java
--------------
Present as both:
- a limitation;
- a methodological necessity.

Recommended wording:
"ReachabilityBench uses generated Java programs rather than real-world repositories. This limits direct ecological validity: the benchmark does not capture the full complexity of naming conventions, architectural patterns, dependencies, side effects, or domain semantics found in real projects. However, this synthetic design is intentional. It allows us to control structural difficulty, generate balanced positive and negative queries, compute exact oracle labels and traces, and validate instances automatically."

Elementary capability
---------------------
State explicitly:
- method reachability is one elementary structural task;
- strong performance does not imply full SE competence;
- poor performance reveals weakness on a controlled sub-capability.

Java only
---------
Current benchmark targets Java.

But:
- generator starts from abstract call graphs;
- core design is partly language-agnostic;
- extending to other languages would require new materialization/validation backend and prompt examples.

Single-class scope
------------------
Current benchmark:
- one Java class;
- many methods;
- calls between methods.

Out of scope:
- inheritance;
- interfaces;
- dynamic dispatch;
- overloading;
- exceptions;
- recursion;
- external libraries;
- multi-class projects.

Acyclic graphs
--------------
Current graphs are acyclic tree-shaped structures.
No cycles or recursion.

Condition-aware scope
---------------------
Condition-aware calls are guarded only by if statements.
Do not claim arbitrary control-flow or loop-guarded call reachability.

Reasoning text limitation
-------------------------
Even though models are local and emitted reasoning can be collected, do not claim emitted reasoning fully reflects internal computation.
