\section{Experimental Setup}
\label{sec:experimental-setup}

The generator exposes the two task families described in the previous section. In the unguarded family, edge-defining calls are emitted outside guards. In the condition-aware family, a visible call contributes only when the generated values make it executable. Both families can use the same values of \texttt{n\_if}; the recorded generator mode, not this factor, identifies the family. The quantitative results reported here use the condition-aware family.

\subsection{Evaluation Set}
\label{subsec:evaluation-set}

The analyzed condition-aware evaluation set contains 46,656 questions generated from 1,232 Java classes. Half of the questions have a reachable target and half have an unreachable target. The generator exposes the same balanced factor grid for the unguarded family, but no score for that family is reported in this paper. The current results can therefore be studied according to distance, class size, and the generated elements added to the code, but cannot support a measured comparison between families.

\vspace{0.2cm}

The complete generation grid is reported in Appendix~\ref{app:experimental-config}. Keeping these parameters together makes the construction of the evaluation set explicit without interrupting the description of the experimental procedure.

Each instance is stored with the information needed to reproduce its evaluation. This includes the Java source, the question, the signed distance, the generated methods, the executable graph, the prompt, and the generation configuration. Historical chain files, when present in older datasets, are diagnostic artifacts; they neither define a canonical traversal nor enter either primary metric.

\subsection{Models and Inference}
\label{subsec:model-configurations}

We evaluate two instruction-tuned mixture-of-experts models: \texttt{google/gemma-4-26B-A4B-it} and \texttt{Qwen/Qwen3.6-35B-A3B}. Each model receives one request for every question, with a requested reasoning budget of 16,384 tokens.

\vspace{0.2cm}

Inference is performed on the Jean Zay supercomputer through an OpenAI-compatible endpoint provided by vLLM. Both models use the same hardware and general serving protocol. Only the model-specific reasoning parser changes between them. The exact checkpoints and serving parameters are reported in Appendix~\ref{app:experimental-config}.

\subsection{Prompting and Response Parsing}
\label{subsec:parsing}

The system prompt contains the complete generated Java class and defines reachability according to the evaluated task family. The same response format is used in both cases. The model returns a JSON object containing a Boolean field named \texttt{final\_answer} and a \texttt{trace} field containing the ordered method names.

\vspace{0.2cm}

The parser scans the response and retains the last valid JSON object. It accepts Boolean values and their string representations, as well as a trace provided directly as a list or as a serialized list. If no valid object or no final answer can be recovered, the response is marked as \texttt{NO\_RESPONSE}. Method names are not corrected, reordered, or completed before evaluation.

The path rules are those introduced in Section~\ref{sec:benchmark-design}. A positive trace starts from the source, follows executable edges, and ends at the target. A negative trace must cover all methods reachable from the source without including the target. This evaluation accepts different valid exploration orders while rejecting methods that cannot execute.

\vspace{0.2cm}

The analysis is descriptive. We first compute the scores over the complete balanced set and then study how they change with the polarity of the question, the absolute distance, the class size, and the generated code factors. When two factor levels are compared, the other factors are averaged over the balanced grid. These differences are reported in percentage points and are not interpreted as causal effects.

The results in the next section use the 46,656 condition-aware records available for each model. An earlier Gemma scoring directory is excluded because it does not correspond to the final executable-graph evaluation.

\subsection{Reproducibility Artifacts}
\label{subsec:artifact-support}

The condition-aware experiment directory contains the generated programs and executable-graph oracle metadata, together with the prompts, raw model responses, server logs, and scored files. Its configuration records mode \texttt{d}, including for instances where \texttt{n\_if}$=0$. It can therefore be used to reconstruct the aggregates reported in the next section and to verify the family and configuration used for each response.
