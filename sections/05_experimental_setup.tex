\section{Experimental Setup}
\label{sec:experimental-setup}

\subsection{Evaluation Set}
\label{subsec:evaluation-set}

The main evaluation uses the final \benchmark dataset, which contains 46,656 questions generated from 1,232 Java classes. Gemma and Qwen receive exactly the same questions, with 11,664 unguarded questions from programs with \mbox{\texttt{n\_if}$=0$} and 34,992 condition-aware questions from programs with \mbox{\texttt{n\_if}}$\in\{1,3,5\}$. Both groups contain an equal number of reachable and unreachable targets.

The generation grid varies \path{class_size} over $\{100,250,500\}$, \path{n_comment} over $\{0,1\}$, and \path{n_vars}, \path{n_loops}, and \path{n_params} over $\{0,1,2\}$. Together with the four values of \path{n_if}, this gives a balanced grid of 648 configurations. The distances sampled through \path{depths} are $\{1,4,7,10,13,16,19,22,25\}$, with \path{n_questions}=4 questions for each polarity at each distance in every configuration. The Java code, question, executable graph, and generation metadata are retained with each instance.

\subsubsection{Independent Validation}
\label{subsec:oracle-validation}

To validate the oracle, we compiled and instrumented every class in the final \benchmark dataset, covering both task families and all their questions. Each class was executed through its corresponding \texttt{Main} launcher, while the instrumentation recorded method entries and exits, parent invocations, and argument values. This allows us to compare the direct calls and reachable region observed for each invocation with the supplied executable graph, and to check every question label against execution.

The validation found agreement for all 337,200 observed invocations with the executable edges and regions, and for all 46,656 question labels with execution. The original and instrumented programs also produced identical standard output and error streams, with no change to the source hashes.

\subsection{Models and Inference}
\label{subsec:model-configurations}

We evaluate \texttt{google/gemma-4-26B-A4B-it} and \texttt{Qwen/Qwen3.6-35B-A3B}, which we refer to as Gemma and Qwen~\cite{google2026gemma4,qwen2026qwen36}. Inference runs on the Jean Zay supercomputer through a vLLM endpoint~\cite{kwon2023vllm}, using BF16 activations, FP8 quantization, a 262,144-token context limit, and tensor parallelism of one. The respective reasoning parsers are \texttt{gemma4} and \texttt{qwen3}, and each question receives one response.

The main evaluation uses \benchmark~(CO), described in Section~\ref{subsec:prompt-design}, with a requested reasoning budget of 16,384 tokens and a final-answer budget of 2,048 tokens. For \benchmark~(EE), the same classes, questions, labels, and oracles are used with a reasoning budget of 32,768 tokens. This increase gives the models more room to follow values from the entry point and evaluate execution, since the two prompts need not require the same amount of reasoning. The comparison therefore concerns the complete inference configurations, in which both prompt and budget change. Section~\ref{sec:error-analysis} examines the tokens actually consumed.

We also evaluate Qwen3.8-Flash-Next with both prompts at the same requested reasoning budget of 16,384 tokens. This comparison uses 216 shared questions from six classes, with 72 questions at each \path{class_size}, and fixes \path{n_comment}=1, \path{n_vars}=2, \path{n_loops}=2, \path{n_if}=5, and \path{n_params}=2. These examples allow us to examine guarded calls and value propagation in difficult configurations, although they do not cover the full factorial grid.

\subsection{Response Parsing and Metrics}
\label{subsec:parsing}
\label{subsec:scoring}
\label{subsec:statistical-analysis}

The parser keeps the last valid JSON object in the response, accepting Boolean values or their string representations and traces given as lists or serialized lists. A response is marked \texttt{NO\_RESPONSE} when no answer can be recovered. The parser does not repair, reorder, or complete method names, so the answer and trace are evaluated as returned, using the executable-graph oracle. Non-responses remain in both score denominators.

For a returned trace $X=\langle x_0,\ldots,x_n\rangle$, the first method must be the source $s$, and no method can appear more than once. Each subsequent method must be introduced through an executable edge from a method already present in the trace:
\[
    \forall i>0,\quad \exists j<i:\ (x_j,x_i)\in E_{\mathit{exec}}.
\]
The trace must end at $t$ for a positive question, while it must contain exactly $R_e(s)$ and exclude $t$ for a negative question. This allows independent branches to be explored in different orders, as illustrated in Figure~\ref{fig:canonical-traversal}. The Boolean answer is compared with $y$ separately, so its correctness does not depend on whether the trace is valid.

To analyze errors, we examine methods omitted from the executable region and existing methods included outside it. An error is attributed to a false guard only when that guard uniquely explains a method introduced without executable support. We also examine value propagation by counting the method boundaries between an exposed guard and the declaration supplying its tested value. A guard is considered exposed when its containing method appears in the trace. The corresponding origin-distance comparisons exclude literal conditions, unresolved origins, and ambiguous attributions. The absence of an attributed error does not establish that the model evaluated the guard correctly.

Token counts are reconstructed from the saved prompts and outputs using each model's tokenizer, with separate counts for the initial prompt, reasoning, and final answer. These measurements therefore describe reconstructed token lengths rather than usage reported by the server. The summaries use the same shared questions and retain all responses for which the corresponding count is available.

The analysis uses descriptive comparisons, averaging over the other factors in the balanced grid and expressing score differences in percentage points. Prompt comparisons use questions shared by both variants within each model, with separate scores by polarity where relevant. Since questions from the same class are related, these comparisons do not treat them as independent observations or report significance tests or causal effects. The archives retain prompts, responses, logs, scored files, and diagnostic populations, while the aggregation scripts check the primary scores and export their counts, denominators, and source hashes.
