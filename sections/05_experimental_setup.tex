\section{Experimental Setup}
\label{sec:experimental-setup}

\subsection{Evaluation Set}
\label{subsec:evaluation-set}

The main evaluation uses the final \benchmark dataset, containing 46,656 questions generated from 1,232 Java classes. Gemma and Qwen are evaluated on exactly the same questions. Programs with \path{n_if}=0 provide 11,664 unguarded questions, while programs with \path{n_if}$\in\{1,3,5\}$ provide 34,992 condition-aware questions. Both groups contain the same number of reachable and unreachable targets.

The grid varies \path{class_size} over $\{100,250,500\}$, \path{n_comment} over $\{0,1\}$, and \path{n_vars}, \path{n_loops}, and \path{n_params} over $\{0,1,2\}$. The four values of \path{n_if} complete a balanced grid of 648 configurations. The values of \path{depths} are $\{1,4,7,10,13,16,19,22,25\}$. \path{n_questions}=4 sets the number of questions for each polarity at each distance in every configuration. Each instance retains the Java code, question, executable graph, and generation metadata.

\subsubsection{Independent Validation}
\label{subsec:oracle-validation}

The validation covers the complete final \benchmark dataset, including both unguarded and condition-aware classes and all their questions. We compiled and instrumented every class independently, starting its execution through the corresponding \texttt{Main} launcher. The instrumentation records method entries and exits, parent invocations, and argument values. This allows us to compare the direct calls and reachable region observed for each invocation with the executable graph supplied with the class, and to check every question label against execution.

All 337,200 observed invocations agreed with the executable edges and regions, and all 46,656 question labels agreed with execution. Original and instrumented programs produced identical standard output and error streams, and source hashes remained unchanged. This validation concerns the specified rooted execution; it does not establish behavior under arbitrary alternative arguments. The maintained generator records a seed, schema version, and source revision, but the historical configurations do not recover their original seed or generator revision.

\subsection{Models and Inference}
\label{subsec:model-configurations}

We evaluate \texttt{google/gemma-4-26B-A4B-it} and \texttt{Qwen/Qwen3.6-35B-A3B}, referred to as Gemma and Qwen~\cite{google2026gemma4,qwen2026qwen36}. Inference runs on the Jean Zay supercomputer through a vLLM endpoint~\cite{kwon2023vllm}. The configuration uses BF16 activations, FP8 quantization, a 262,144-token context limit, tensor parallelism of one, and the respective \texttt{gemma4} and \texttt{qwen3} reasoning parsers. Each question receives one response.

The main evaluation uses \benchmark~(CO), described in Section~\ref{subsec:prompt-design}, with a requested reasoning budget of 16,384 tokens and a final-answer budget of 2,048 tokens. The comparison with \benchmark~(EE) uses the same Java classes, questions, labels, and oracles, with a reasoning budget of 32,768 tokens. This larger budget gives the models more room to follow values from the entry point and evaluate execution, since the two prompts need not lead to the same amount of reasoning. Both the prompt and budget change in this comparison, so the results describe the complete inference configurations. Section~\ref{sec:error-analysis} examines the tokens actually consumed.

We also evaluate Qwen3.8-Flash-Next with CO and EE using the same requested reasoning budget of 16,384 tokens. This experiment contains 216 shared questions from six classes, with 72 questions at each \path{class_size}. The questions use \path{n_comment}=1, \path{n_vars}=2, \path{n_loops}=2, \path{n_if}=5, and \path{n_params}=2. These examples allow us to examine guarded calls and value propagation in difficult configurations, but do not cover the full factorial grid.

\subsection{Response Parsing and Metrics}
\label{subsec:parsing}
\label{subsec:scoring}
\label{subsec:statistical-analysis}

The parser keeps the last valid JSON object in the response. It accepts Boolean values or their string representations, and traces given as lists or serialized lists. When no answer can be recovered, the response is marked \texttt{NO\_RESPONSE}. Method names are not repaired, reordered, or completed. The final answer and trace are then evaluated separately using the executable-graph oracle. Non-responses remain in both score denominators.

Let $X=\langle x_0,\ldots,x_n\rangle$ be the returned trace. The first method must be the source $s$, and no method can appear more than once. Each later method must also be introduced through an executable edge from a method that has already appeared in the trace:
\[
    \forall i>0,\quad \exists j<i:\ (x_j,x_i)\in E_{\mathit{exec}}.
\]
For a positive question, the trace must end at $t$. For a negative question, it must contain exactly $R_e(s)$ and exclude $t$. These rules allow independent branches to be explored in different orders, as illustrated in Figure~\ref{fig:canonical-traversal}. The Boolean answer is compared with $y$ independently of whether the trace is correct.

To analyze errors, we examine methods omitted from the executable region and existing methods included outside it. An error is attributed to a false guard only when this guard uniquely explains a method introduced without executable support. To examine value propagation, we count the method boundaries between an exposed guard and the declaration supplying its tested value. A guard is exposed when its containing method appears in the returned trace. Literal conditions, unresolved origins, and ambiguous attributions are excluded from the corresponding origin-distance comparisons. A guard without an attributed error is not necessarily evaluated correctly by the model.

Token counts are reconstructed from the saved prompts and outputs using the model tokenizers. We count the initial prompt, reasoning, and final answer separately. These are reconstructed counts, rather than usage reported by the server. Token summaries use the same shared questions and retain all responses for which the corresponding count is available.

The analysis is descriptive. For each factor, we average over the other factors in the balanced grid and express score differences in percentage points. Prompt comparisons use questions shared by both variants within each model, with separate scores by polarity where relevant. Since questions from the same class are related, we do not treat them as independent observations or report significance tests or causal effects. The archives retain prompts, responses, logs, scored files, and diagnostic populations. The aggregation scripts check the primary scores and export their counts, denominators, and source hashes.
