Software-engineering benchmarks often measure whether a model completes a task while combining several capabilities in the same problem. We propose \benchmark, a configurable benchmark for executable method reachability in generated Java programs. Its call graphs provide Boolean labels and an oracle that evaluates returned exploration traces without requiring one canonical order. We evaluate Gemma~4 and Qwen~3.6 on 46,656 shared questions, separating unguarded programs (\texttt{nb\_if}$=0$) from condition-aware programs (\texttt{nb\_if}$>0$). Qwen obtains 87.98\% final-answer correctness and 67.43\% path correctness; Gemma obtains 84.21\% and 55.90\%. Trace accuracy deteriorates especially when conditions depend on passed values and when negative queries require exhaustive exploration. Attributed guard errors involve more distant value origins than exposed guards without detected errors. Their ability to lead toward the target also helps explain opposing changes in positive and negative answer accuracy as classes grow. These descriptive findings show how a correct reachability decision can conceal incomplete or non-executable supporting evidence.
