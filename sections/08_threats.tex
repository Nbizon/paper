\section{Discussion and Threats to Validity}
\label{sec:discussion}

\subsection{What the Benchmark Measures}

\benchmark measures whether a model can produce a correct reachability answer and a trace that is consistent with the executable program. It does not observe the internal reasoning that produced these outputs. A correct trace may be generated for the wrong reason, and an incorrect trace may be produced after the model has already selected the correct answer. For this reason, we interpret the trace as additional evidence about model behavior and not as a direct explanation of its internal computation.

Path correctness depends on the generated executable graph. Although this avoids privileging one canonical traversal, any error in executable-edge generation would affect every path score. We mitigate this threat by auditing labels and generated chains against the graph and by reporting the Boolean and path metrics independently.

\subsection{What Can Affect the Experiment}

The result of an instance depends on several stages: graph generation, Java generation, oracle construction, prompting, inference, parsing, and scoring. An error in any of these stages can be interpreted incorrectly as a model error. We validate the generated classes by compiling them and recomputing their calls, conditions, labels, and traces. We also use the same parser for all models and calibrate the prompt on a separate pilot set.

Inference introduces additional variation. A different model revision, backend, chat template, context limit, or decoding parameter can change the output even when the checkpoint name remains the same. The experiment therefore records complete model configurations and uses deterministic decoding when possible. These controls reduce variation, but they do not make two different deployments equivalent.

\subsection{What the Results Can Generalize To}

The generated programs provide control because their complete call graphs are known. The same choice also removes many properties of real software. A generated single-class program does not reproduce the naming conventions, domain logic, dependencies, side effects, or architecture of a repository. The results therefore describe a controlled method-reachability task and should not be interpreted as direct performance on debugging, repair, or code review.

The current call graphs are acyclic trees. The generated programs do not cover inheritance, interfaces, dynamic dispatch, overloading, exceptions, recursion, external libraries, multiple classes, or cyclic calls. They also use limited data flow, and condition-aware reachability is currently introduced through generated \texttt{if} statements. Extending the benchmark with one of these elements would create a new factor that requires its own generator and oracle validation.

The graph-level task is not specific to Java. Another language could reuse the call-graph generation, question selection, and trace convention. However, the source generator, compilation or execution checks, and prompt examples would need to be adapted. Results should not be compared across languages until these language-specific differences are controlled.

\subsection{What Can Be Concluded from the Scores}

Several questions can be generated from the same class, which creates dependencies between observations. We therefore compute uncertainty by sampling classes rather than individual questions. The unguarded and condition-aware datasets are also not paired by construction. Their difference is analyzed with unpaired intervals unless matched versions are generated.

Strict scores keep \texttt{NO\_RESPONSE} in the denominator. This choice measures the complete evaluated system, but it combines task errors with formatting and serving failures. We therefore report \texttt{NO\_RESPONSE} separately and distinguish final-answer accuracy from trace metrics. Reasoning-budget results are also limited to configurations for which the control is verified. These choices prevent a single aggregate score from supporting a conclusion that the experiment does not isolate.
