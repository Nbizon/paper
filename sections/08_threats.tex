\section{Discussion and Threats to Validity}
\label{sec:discussion}

\subsection{Construct Validity}

\benchmark evaluates two outputs: a Boolean answer and a generated trace. These outputs do not provide direct access to the internal reasoning of the model. A model can produce the correct trace for the wrong reason, or select the correct final answer before generating an inconsistent trace. Generated reasoning text has the same limitation because it is an observable output and not a complete representation of the internal computation. To limit the interpretation of a single metric, we report final-answer accuracy, trace quality, graph validity, and parsing failures together.

The canonical trace is also based on a convention defined by the benchmark. It follows executable calls in source order and is not always the shortest way to demonstrate reachability. Exact trace accuracy therefore measures whether a model follows this specific convention. Graph-valid exploration and trace completeness provide less restrictive measures of whether the predicted trace is structurally correct.

\subsection{Internal Validity}

The main internal risks are errors in the generator or validator, ambiguous instructions, parsing errors, and inference parameters that are not controlled. The validator compiles every generated class and checks its method calls, labels, traces, guard results, and graph metadata. Prompt calibration is performed on a separate pilot set, and the deployment manifests record the parameters used for each model configuration. The same conservative parsing rules are applied to all model responses.

These checks do not remove the need for a final stabilized experiment. The datasets, prompts, model revisions, serving parameters, and evaluation scripts must be frozen before quantitative results are used in the paper.

\subsection{External Validity}

Using generated Java programs gives \benchmark precise experimental control, but it also limits the generalization of its results. Real repositories contain naming conventions, domain-specific logic, dependencies, side effects, and architectural structures that are not reproduced in the generated classes. Performance on \benchmark should therefore be interpreted as evidence about a controlled program-structure task. It is not a direct estimate of performance on complete software-maintenance tasks.

The current programs contain a single class and an acyclic tree of methods. They do not include inheritance, interfaces, dynamic dispatch, overloading, exceptions, recursion, external libraries, multiple classes, cyclic call graphs, realistic identifiers, complex data flow, or reachability controlled by arbitrary loops. Condition-aware calls are currently limited to generated \texttt{if} statements. These elements can be added in future versions, but each extension introduces new factors that must be generated and validated separately.

The abstract call graphs are not specific to Java. The same graph generation, question sampling, and trace conventions could be used for another programming language. However, such a version would require a language-specific source generator, compiler or runtime validation, and adapted prompt examples before its results could be compared with the Java version.

\subsection{Conclusion Validity}

The available numerical results are preliminary and are not used to support the conclusions of this draft. In the final analysis, \texttt{NO\_RESPONSE} must remain in the denominator of strict scores. Final-answer accuracy, trace quality, structural effects, differences between deployed configurations, and verified reasoning-budget effects must also be reported separately. Unguarded and condition-aware instances are not paired by construction, and analyzing them as paired observations would underestimate uncertainty.

The results can also be affected by the prompt, JSON extraction rules, serving backend, decoding parameters, and model revision. We record these choices and compute clustered confidence intervals, but the analysis remains limited to the configurations that were evaluated. In particular, conclusions about reasoning budgets remain part of \researchq{2} unless the final experiments show that the same effect is present in both task families.
