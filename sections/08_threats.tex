\section{Discussion and Limitations}
\label{sec:discussion}

\subsection{Complementarity with Realistic Benchmarks}

\benchmark is a diagnostic benchmark, not a replacement for realistic software-engineering benchmarks. Existing code benchmarks are valuable for measuring end-to-end performance on realistic tasks. \benchmark is complementary: it isolates a lower-level structural capability that may be hidden inside broader software-engineering tasks.

\subsection{Synthetic Java}

\benchmark uses generated Java programs rather than real-world repositories. This limits direct ecological validity: the benchmark does not capture the full complexity of naming conventions, architectural patterns, dependencies, side effects, or domain semantics found in real projects. However, this synthetic design is intentional. It allows us to control structural difficulty, generate balanced positive and negative queries, compute exact oracle labels and traces, and validate instances automatically.

\subsection{Task Scope}

The current benchmark targets Java and materializes each instance as a single class containing many generated methods. It does not include inheritance, interfaces, dynamic dispatch, overloading, exceptions, recursion, external libraries, multi-class projects, or cyclic call graphs. Current graphs are acyclic tree-shaped structures. Condition-aware reachability is limited to \texttt{if} statements and does not claim arbitrary control-flow or loop-guarded call reachability.

The generator starts from abstract call graphs, so the core design is partly language-agnostic. Extending the benchmark to other languages would require a new materialization and validation backend, as well as language-specific prompt examples.

\subsection{Trace and Reasoning Limitations}

Trace correctness is an observable-output metric, not a direct measurement of hidden model cognition. A model may produce a correct trace for the wrong internal reason, or a correct final answer with an invalid trace. Likewise, emitted reasoning text from locally run models is an observable output artifact; we do not assume that it fully captures internal computation.
