\section{Introduction}

Large language models are increasingly used for software-engineering tasks such as debugging, code review, program repair, and program comprehension. Benchmarks that approximate developer workflows are therefore essential: they assess whether a system can solve useful tasks under realistic constraints on context, tooling, and output. However, aggregate benchmark scores often say little about which code-structural properties drive success or failure. A model may succeed because it follows executable structure, recognizes informative names, exploits surface syntax, uses tests effectively, or simply guesses a plausible answer.

This ambiguity is especially pronounced in realistic tasks, where failures can stem from many sources: incorrect localization, weak semantic reasoning, missing API knowledge, flawed edits, output-format violations, or a mismatch between the prompt and the intended abstraction. Successes are similarly difficult to interpret, since they may reflect either robust program understanding or shortcuts exposed by particular benchmark instances. Existing realistic benchmarks are valuable precisely because they test models under real-world conditions, but they are not designed to isolate the mechanisms behind structural reasoning failures.

We study executable method reachability as a compact diagnostic problem for program-structure reasoning. Given a Java program, a source method, and a target method, the task asks whether execution starting at the source can reach the target through direct or indirect method calls. Our goal is not to evaluate whether language models can match or replace static or dynamic analysis tools. Instead, we use reachability as a controlled diagnostic lens: the task admits exact oracle labels and traces, while still requiring reasoning over inter-method program structure rather than over a single expression or statement.

\benchmark operationalizes this lens through generated Java programs with oracle labels, canonical traces, and controlled structural factors. Each instance consists of a single-class program paired with a source--target query. The benchmark includes two task families. In \emph{unguarded reachability}, all generated visible calls execute, so syntactic call visibility and executable reachability coincide. In \emph{condition-aware reachability}, selected visible calls are placed behind generated guards whose evaluated conditions may disable the call, creating an explicit gap between the syntactic and executable call graphs.

The benchmark separates final-answer correctness from trace behavior. A correct \true/\false answer may still hide a shortcut, omit an intermediate call, include an invalid transition, or reveal a syntactic-call bias, where a model treats a visible but disabled call as executable. Requiring a trace makes these distinctions observable. \benchmark therefore measures not only whether a model predicts reachability correctly, but also whether its reported exploration follows the validated executable structure.

This paper makes the following contributions:
\begin{itemize}[leftmargin=*]
    \item \textbf{A controlled Java benchmark for executable reachability.}
    \benchmark provides generated inter-method reachability instances with oracle labels, canonical traces, and metadata for factor-level analysis.

    \item \textbf{A trace-aware evaluation suite.}
    We measure final-answer accuracy, exact canonical trace accuracy, trace completeness, graph-valid exploration, syntactic-call bias, and invalid-output behavior.

    \item \textbf{An empirical study and artifact.}
    We evaluate \texttt{[N\_MODELS]} locally served LLM configurations on \texttt{[N\_INSTANCES]} generated instances and provide an anonymized artifact containing generation, prompting, parsing, evaluation, and analysis scripts.
\end{itemize}
