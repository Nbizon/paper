\section{Introduction}

Large language models are increasingly used for software-engineering tasks such as debugging, code review, repair, and program comprehension. Benchmarks that approximate developer workflows are therefore indispensable: they test whether a system can solve useful tasks under realistic context, tooling, and output constraints. At the same time, their aggregate scores often do not identify which code-structural properties caused success or failure. A model may appear competent because it followed executable structure, recognized names, exploited surface syntax, used tests effectively, or guessed a plausible answer.

This attribution problem matters for scientific progress. When a model fails on a realistic task, the failure may come from localization, semantic reasoning, API knowledge, editing, output formatting, or a mismatch between the prompt and the intended abstraction. When a model succeeds, the success may likewise reflect robust program understanding or a shortcut exposed by the benchmark instance. Existing realistic benchmarks are valuable precisely because they combine these capabilities, but they are not designed to isolate the mechanisms behind structural reasoning failures.

We study executable method reachability as a compact diagnostic problem for program-structure reasoning. Given a Java program, a source method, and a target method, the task asks whether execution starting at the source can reach the target through direct or indirect method calls. We do not propose this task as a replacement for static or dynamic analysis tools. We use it as a controlled diagnostic lens: executable reachability admits exact oracle labels and traces, yet still requires reasoning over inter-method program structure rather than over a single expression or statement.

\benchmark applies this lens through generated Java programs with oracle labels, canonical traces, and controlled structural factors. Each instance is a single-class program paired with a source--target query. The benchmark has two task families. In \emph{unguarded reachability}, all generated visible calls execute, so syntactic call visibility and executable reachability coincide. In \emph{condition-aware reachability}, selected visible calls are placed behind generated guards whose evaluated conditions can disable the call, creating an explicit gap between the syntactic and executable call graphs.

The benchmark separates final-answer correctness from trace behavior. A correct \true/\false answer can hide a shortcut, a missing intermediate call, an invalid transition, or a syntactic-call bias in which a model treats a visible but disabled call as executable. Requiring a trace makes these differences observable. \benchmark therefore measures not only whether a model predicts reachability, but also whether its reported exploration follows the validated executable structure and the benchmark's canonical order.

This paper makes the following contributions:
\begin{itemize}[leftmargin=*]
    \item \textbf{A controlled Java benchmark for executable reachability.} \benchmark provides generated inter-method reachability instances with oracle labels, canonical traces, and metadata for factor-level analysis.
    \item \textbf{A condition-aware task family.} The benchmark separates syntactic call visibility from executable reachability by placing selected calls behind generated guards.
    \item \textbf{A trace-aware evaluation suite.} We measure final-answer accuracy, exact canonical trace accuracy, trace completeness, graph-valid exploration, syntactic-call bias, and invalid-output behavior.
    \item \textbf{An empirical study and artifact.} We evaluate \texttt{[N\_MODELS]} locally served LLM configurations on \texttt{[N\_INSTANCES]} generated instances and provide an anonymized artifact containing generation, prompting, parsing, evaluation, and analysis scripts.
\end{itemize}
