\section{Introduction}

LLMs are now widely used in software engineering, particularly to assist developers with tasks such as program understanding, debugging, code review, and code generation. To evaluate their capabilities on these tasks, many benchmarks have been proposed with the objective of reproducing problems that are close to those encountered by developers.

Benchmarks such as HumanEval and SWE-bench evaluate whether a model produces code that passes tests or resolves a repository issue~\cite{chen2021codex,jimenez2024swebench}. These tasks can involve several capabilities at the same time, which makes it difficult to identify the reasons behind a model's success or failure from the final result alone. Recent benchmarks also evaluate specific program properties. SemBench includes function reachability as a static call-graph task, while TraceEval asks models to recover runtime call structures from repository code~\cite{xu2026semb,li2026traceeval}. ReachabilityBench addresses a different question: whether a target method executes from a selected source under the concrete values supplied by one generated execution. Calls visible in the class can be excluded when their guards evaluate to false, and values passed between methods can determine which calls execute.

In this work, we propose \benchmark, a generated Java benchmark whose objective is to evaluate executable method reachability. \benchmark is the final dataset of Java classes, questions, labels, and executable-graph oracles; a separate configurable construction algorithm produces these elements. The same dataset is evaluated with two prompt variants, \benchmark~(CO) and \benchmark~(EE), which differ in whether the entry point and deterministic execution assumptions are made explicit.

The generated programs vary in structure and in the values that determine which calls can execute. For each question, the model returns a Boolean answer and an exploration trace. A positive trace must provide an executable route to the target, while a negative trace must cover the complete region reachable from the source. The oracle accepts different valid exploration orders, and the labels and executable graphs are checked by running the complete final dataset.

This paper makes three contributions:
\begin{itemize}[leftmargin=*]
    \item the final \benchmark dataset of 1,232 Java classes and 46,656 questions, produced by a configurable algorithm that controls method structure, guarded execution, and code presentation;
    \item an execution-validated oracle that scores Boolean decisions separately from graph-supported exploration traces, requiring a complete reachable region for negative answers while accepting different valid exploration orders;
    \item an empirical analysis showing that answer correctness exceeds trace correctness, with errors concentrated around guarded calls, passed values, and negative questions, as well as a comparison of CO and EE and a Qwen3.8-Flash-Next study on difficult examples.
\end{itemize}
