\section{Introduction}

LLMs are now widely used in software engineering, particularly to assist developers with program understanding, debugging, code review, and code generation. Understanding which methods can execute from a given source is relevant when a developer investigates a behavior or inspects the code potentially affected by a change. Such a question requires following calls and, when they are guarded, the values that determine whether they execute.

Many benchmarks evaluate whether a model completes a development task, such as producing code that passes tests or resolving a repository issue~\cite{chen2021codex,jimenez2024swebench}. A single outcome can combine several capabilities, making it difficult to locate the source of a failure. More focused benchmarks already examine runtime behavior, program dependencies, and call structure~\cite{chen2025reval,xie2025core,li2026traceeval}. These studies motivate evaluating the program relationships recovered by a model and the evidence supporting its answer.

In this work, we propose \benchmark, a generated Java benchmark for executable method reachability. Given a source method and a target method, the model determines whether the latter can execute from the former under the program's fixed execution context. \benchmark is the final dataset of classes, questions, Boolean labels, and executable-graph oracles. A separate configurable construction algorithm produces these elements together.

The generated programs vary in structure and in the values that determine which calls can execute. This allows us to examine how these properties affect the model's reachability decisions and the evidence it provides.

Our contribution combines this control with separate evaluation of the Boolean decision and the returned exploration trace. The oracle accepts different exploration orders supported by executable calls. It therefore reveals unsupported calls or omissions even when the final decision is correct. Both labels and executable graphs are independently checked by running the complete final dataset.

We also compare \benchmark~(CO) and \benchmark~(EE), two prompting variants of the same dataset. CO leaves the entry point and determinism implicit, while EE makes them explicit. This comparison examines how the supplied execution information relates to performance and token consumption.

This paper makes three contributions:
\begin{itemize}[leftmargin=*]
    \item a benchmark of 1,232 Java classes and 46,656 questions, together with its configurable construction algorithm, controlling call structure, guarded execution, and presentation factors;
    \item an evaluation of reachability decisions and exploration traces against execution-validated labels and graphs, accepting valid exploration orders without requiring one canonical sequence;
    \item an empirical study of Gemma~4 and Qwen~3.6 that locates difficulties with guarded calls, passed values, and exhaustive exploration, complemented by the CO/EE comparison and a Qwen3.8-Flash-Next study on difficult instances.
\end{itemize}
