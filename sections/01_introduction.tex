\section{Introduction}

LLMs are now widely used in software engineering to assist developers with tasks such as program understanding, debugging, code review, and code generation. To evaluate these capabilities on tasks that resemble software development, many benchmarks have been proposed, including HumanEval and SWE-bench~\cite{chen2021codex,jimenez2024swebench}.

However, these benchmarks mainly provide a global measure of whether a model can solve a task. Since a task can involve several capabilities at once, its final score often gives little information about the reasons behind success or failure. A correct or incorrect answer alone may also hide what evidence the model used. For example, a model may rely on semantic information in method or variable names, but the final answer does not show whether this information affected its decision.

In this work, we propose \benchmark, a Java benchmark that complements existing benchmarks with a finer-grained analysis of model behavior. It focuses on executable reachability between methods. Given a Java class containing multiple methods and a question specifying a source and a target method, the model must determine whether the target can execute from the source for the argument values supplied by one generated execution. Calls in the class may be guarded, so their presence in the code does not mean that they execute. Determining which calls execute can require following values passed between methods.

The Java code is generated from known call structures by a separate configurable construction algorithm. The resulting \benchmark dataset contains the classes, reachability questions, Boolean labels, and executable graphs. The algorithm controls class size, guarded calls, values passed between methods, and target distance. This makes it possible to compare model behavior across structural difficulties.

Since the executable graph is known, each question has an oracle label and a graph against which model traces can be checked. Each response is a JSON object with a \texttt{final\_answer} indicating \texttt{True} or \texttt{False}, and a \texttt{trace} listing the methods explored. We check the answer against its label and the trace against the graph. A positive trace must end at its target, while a negative trace must cover all methods reachable from the source. Different valid exploration orders are accepted. The trace provides information beyond the Boolean answer, but it is an output to evaluate rather than a direct record of the model's internal reasoning.

We compare two prompt variants of \benchmark: Class-only (CO) and Explicit execution (EE). Both use the same classes, questions, labels, and executable graphs. CO presents the class without a launcher and leaves the entry point and deterministic execution implicit. EE adds a separate \texttt{Main} launcher and states that the relevant values and execution outcomes are determined by the code. CO therefore requires the model to infer execution context that EE makes explicit.

This paper makes three contributions:
\begin{itemize}[leftmargin=*]
    \item the final \benchmark dataset of 1,232 Java classes and 46,656 questions, with parameters that vary structural difficulty.
    \item an evaluation that checks Boolean answers against labels and method traces against the executable graph.
    \item an empirical study of model performance across structural factors and the CO and EE prompt variants.
\end{itemize}
