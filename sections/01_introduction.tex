\section{Introduction}

Large language models are increasingly evaluated on software-engineering tasks that resemble developer work: debugging, code review, patch generation, program explanation, and reasoning about where a behavior can occur. This move toward realistic tasks is necessary, but it also makes results harder to interpret. A model may solve an issue because it followed the relevant program structure, recognized a familiar API pattern, exploited a test signal, or produced a plausible patch despite only partial understanding. When these signals are entangled, aggregate success rates do not explain which code properties actually caused success or failure.

This paper studies that attribution problem through executable method reachability. The goal is not to argue that reachability is the most important software-engineering task, or that language models should replace mature static and dynamic analysis tools. Reachability is useful here because it is small enough to control and semantic enough to be checked precisely: for a generated Java program, we can know whether one method can execute another, which path the benchmark treats as canonical, and whether a model's trace follows executable calls rather than surface syntax.

We introduce \benchmark, a diagnostic Java benchmark built around this setting. \benchmark generates tree-shaped, single-class programs with oracle labels and execution-oriented traces. It varies canonical execution distance, class size, query polarity, and condition-aware guards. In the unguarded family, visible generated calls are executable. In the condition-aware family, some visible calls appear behind generated \texttt{if} conditions that make them non-executable. The benchmark therefore separates two abilities that are often conflated in code understanding: noticing textual call sites and reasoning about executable behavior.

\benchmark is designed to complement, not replace, broader software-engineering benchmarks. Its contribution is factor control. Because labels, traces, and task parameters are known by construction, failures can be analyzed by the properties that produced them rather than only by aggregate task success. A final \true/\false answer may hide shortcuts, invalid transitions, missing intermediate methods, or syntactic-call bias; the trace requirement makes those distinctions observable. The empirical question is whether LLM systems can recover the validated executable structure and trace convention from source code alone.

This paper makes the following contributions:
\begin{itemize}[leftmargin=*]
    \item \textbf{A parameterized diagnostic benchmark.} \benchmark evaluates executable inter-method reachability while varying distance, class size, and condition-aware guards under oracle supervision.
    \item \textbf{Trace-aware evaluation.} We measure final-answer correctness together with exact canonical trace accuracy, trace completeness, graph-valid exploration, syntactic-call bias, and invalid-output behavior.
\end{itemize}
