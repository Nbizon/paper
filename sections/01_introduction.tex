\section{Introduction}

LLMs are now widely used in software engineering, particularly to assist developers with tasks such as program understanding, debugging, code review, and code generation. To evaluate their capabilities on these tasks, many benchmarks have been proposed with the objective of reproducing problems that are close to those encountered by developers.

Benchmarks such as HumanEval and SWE-bench evaluate whether a model produces code that passes tests or resolves a repository issue~\cite{chen2021codex,jimenez2024swebench}. These tasks can involve several capabilities at the same time, which makes it difficult to identify the reasons behind a model's success or failure from the final result alone. Other benchmarks focus more directly on runtime behavior, program dependencies, and call structure~\cite{chen2025reval,xie2025core,li2026traceeval}. These evaluations make it possible to study which program relationships the model identifies and what evidence it provides for its answer.

In this work, we propose \benchmark, a generated Java benchmark whose objective is to evaluate executable method reachability. Given a source method and a target method, the model must determine whether the target can execute from the source under the execution context fixed by the program. \benchmark is the final dataset containing the classes, questions, Boolean labels, and executable-graph oracles. A separate configurable construction algorithm produces these elements together.

The generated programs vary in structure and in the values that determine which calls can execute. This allows us to examine how these properties affect the model's reachability decisions and the evidence it provides.

Our approach combines this control with a separate evaluation of the Boolean answer and the exploration trace returned by the model. The oracle accepts different exploration orders, as long as the calls followed by the model can execute. This makes it possible to detect unsupported calls or omitted methods even when the final answer is correct. The labels and executable graphs are also checked independently by running the complete final dataset.

We consider two prompting variants of this same dataset, \benchmark~(CO) and \benchmark~(EE). In CO, the entry point and deterministic execution assumptions remain implicit, while EE makes them explicit. Comparing these variants allows us to examine how the execution information supplied to the model relates to its performance and token consumption.

This paper makes three contributions:
\begin{itemize}[leftmargin=*]
    \item a benchmark of 1,232 Java classes and 46,656 questions, together with the configurable algorithm used to construct them and control call structure, guarded execution, and presentation factors;
    \item an evaluation that checks reachability decisions and exploration traces separately, using labels and graphs verified by execution and accepting different valid exploration orders;
    \item a study of Gemma~4 and Qwen~3.6 that examines difficulties with guarded calls, passed values, and exhaustive exploration, together with the CO/EE comparison and a Qwen3.8-Flash-Next study on difficult examples.
\end{itemize}
