\section{Introduction}

LLMs are now widely used in software engineering, particularly to assist developers with tasks such as program understanding, debugging, code review, and code generation. To evaluate their capabilities on these tasks, many benchmarks have been proposed with the objective of reproducing problems that are close to those encountered by developers.

Benchmarks such as HumanEval and SWE-bench evaluate whether a model produces code that passes tests or resolves a repository issue~\cite{chen2021codex,jimenez2024swebench}. These tasks can involve several capabilities at the same time, which makes it difficult to identify the reasons behind a model's success or failure from the final result alone. Other benchmarks evaluate specific program properties. SemBench includes function reachability based on a static call graph, while TraceEval asks models to recover runtime call structures from repository code~\cite{xu2026semb,li2026traceeval}. ReachabilityBench asks whether a target method executes from a selected source under values supplied by one generated execution. Calls behind false guards remain visible in the class, but do not execute. Values passed between methods determine which guarded calls are active.

In this work, we propose \benchmark, a generated Java benchmark for executable method reachability. \benchmark is the final dataset of Java classes, questions, labels, and executable-graph oracles. A separate configurable construction algorithm generates it. Parameters such as \path{class_size}, \path{n_if}, \path{n_params}, and \path{depths} vary class size, guarded execution, parameter flow, and target distance. This allows us to compare model behavior across controlled structural difficulties. CO and EE are two prompt variants over the same dataset. EE makes the entry point and deterministic execution assumptions explicit, while CO leaves them implicit.

Each answer includes a Boolean decision and a trace listing the explored methods. The trace gives more information about the answer. It shows which methods the model explores, and we check whether they are connected by calls that execute. A positive trace must reach the target. A negative trace must cover the complete region reachable from the source. The evaluator accepts different valid exploration orders. We check the labels and graphs by running the complete dataset.

This paper makes three contributions:
\begin{itemize}[leftmargin=*]
    \item the final \benchmark dataset of 1,232 Java classes and 46,656 questions. Its parameters vary method structure, guarded execution, and values passed between methods.
    \item a trace evaluation that checks the explored methods against the executable graph. This adds information beyond Boolean correctness and accepts different valid exploration orders.
    \item an empirical analysis showing that answer correctness exceeds trace correctness, with errors concentrated around guarded calls, passed values, and negative questions. We also compare CO and EE and study Qwen3.8-Flash-Next on difficult examples.
\end{itemize}
