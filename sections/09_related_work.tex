\section{Related Work}
\label{sec:related-work}

\subsection{Evaluating Whether a Model Can Complete a Task}

A large part of the evaluation of code-oriented LLMs focuses on whether a model can produce a result that satisfies the required behavior. For code generation, HumanEval, MBPP, and APPS evaluate this by checking generated programs against tests~\cite{chen2021codex,austin2021program,hendrycks2021apps}. CodeXGLUE extends evaluation to both understanding and generation~\cite{lu2021codexglue}, while LiveCodeBench also includes execution and test-output prediction~\cite{jain2025livecodebench}. BigCodeBench considers tasks involving the composition of library calls~\cite{zhuo2025bigcodebench}.

Other evaluations consider problems closer to repository-level development. SWE-bench asks models to resolve issues~\cite{jimenez2024swebench}, while Defects4J provides real Java defects and tests for repair studies~\cite{just2014defects4j}. These settings provide information about whether a system can complete a task, but several capabilities may be required at the same time. An unsuccessful result therefore makes it difficult to identify precisely which part of the task caused difficulty.

\subsection{Evaluating Specific Properties of Program Behavior}

Other works reduce the scope of the task with the objective of examining specific aspects of program understanding. CRUXEval asks models to predict inputs or outputs for short Python functions, while REval evaluates predictions about runtime behavior and intermediate states~\cite{gu2024cruxeval,chen2025reval}. Xie et al.'s CoRE considers static data and control dependencies and information flow, whereas Gao et al.'s CoRE examines implementation invariance and intermediate execution-state prediction~\cite{xie2025core,gao2026core}. This allows model capabilities to be studied through properties that can be evaluated more directly.

Some benchmarks examine relationships between calls. SemBench includes function reachability, defined by connectivity in a static call graph over real-world C programs~\cite{xu2026semb}. TraceEval asks models to recover runtime call structures from repository-derived programs, with edges verified through execution~\cite{li2026traceeval}. CABRA also uses generated call-graph transformations to control difficulty, although its tasks concern code editing with coding agents~\cite{balepur2026cabra}. These works provide related approaches to evaluating code behavior, but differ in the questions asked and the information returned by the model. \subsection{Position of \benchmark}

Call-graph analysis provides a representation for examining possible method calls~\cite{grove2001framework,tip2000scalable}. \benchmark uses this representation to study whether a target executes from a source under values supplied by one generated execution. Its questions therefore concern executable reachability, including whether visible calls are disabled by conditions, rather than static connectivity or recovery of the complete runtime call structure.

A separate configurable construction algorithm controls class size, guarded calls, and values passed between methods. This allows us to compare model behavior across structural difficulties while evaluating the Boolean answer and method trace separately. A correct answer can therefore be distinguished from an exploration that follows executable calls. This controlled setting complements repository-derived evaluations, although it covers a narrower range of Java behavior.
