\section{Related Work}
\label{sec:related-work}

\subsection{Task Completion and Program Understanding}

HumanEval, MBPP, and APPS evaluate generated code through tests~\cite{chen2021codex,austin2021program,hendrycks2021apps}. Their scores indicate whether an implementation satisfies the required behavior, but do not directly identify which program relationships the model understood. CodeXGLUE broadens evaluation to understanding and generation~\cite{lu2021codexglue}, while LiveCodeBench includes execution and test-output prediction alongside generation~\cite{jain2025livecodebench}. BigCodeBench emphasizes the composition of library calls under complex instructions~\cite{zhuo2025bigcodebench}.

Repository-level evaluations cover more complete development tasks. SWE-bench asks a system to modify a repository to resolve an issue~\cite{jimenez2024swebench}, and Defects4J provides real Java defects and tests for studies of repair~\cite{just2014defects4j}. \benchmark complements these settings by isolating method reachability and checking the evidence returned for each decision. It does not establish the ability to complete repository-level tasks.

\subsection{Runtime Behavior and Dependencies}

CRUXEval evaluates input and output prediction for short Python functions~\cite{gu2024cruxeval}. REval studies execution paths, coverage, states, and outputs, including consistency between predictions~\cite{chen2025reval}. These benchmarks motivate the evaluation of checkable runtime properties. \benchmark focuses on executable relationships between methods and accepts different exploration orders supported by its graph oracle.

CoRE evaluates data dependencies, control dependencies, and information flow through human-verified static-analysis tasks~\cite{xie2025core}. This relates to the value propagation required by guarded calls in our programs. TraceEval studies runtime call structure in repository-derived programs~\cite{li2026traceeval}, while RE2-Bench relates reasoning difficulty to program complexity~\cite{liu2025re2bench}. Our complementary choice is to generate structure and values before constructing the class, so that guards, parameters, class size, and distance can be varied in a balanced grid. This control facilitates diagnosis while covering a narrower range of behavior.

\subsection{Reachability and Call-Graph Analysis}

Call-graph analysis studies the information needed to determine possible calls~\cite{grove2001framework,tip2000scalable}. \benchmark uses this graph perspective to evaluate LLM responses, with separate decision and trace scores. Its construction algorithm provides controlled instances, while the evaluation exposes unsupported calls and omissions from the executable region. The prompt comparison additionally examines how these observations change when the entry point and deterministic execution are made explicit.
