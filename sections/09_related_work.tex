\section{Related Work}
\label{sec:related-work}

\subsection{Task Completion and Program Understanding}

HumanEval, MBPP, and APPS evaluate generated code by checking whether it passes tests~\cite{chen2021codex,austin2021program,hendrycks2021apps}. CodeXGLUE extends evaluation to both understanding and generation~\cite{lu2021codexglue}. LiveCodeBench also includes execution and test-output prediction~\cite{jain2025livecodebench}, while BigCodeBench emphasizes the composition of library calls~\cite{zhuo2025bigcodebench}. At the repository level, SWE-bench evaluates issue resolution~\cite{jimenez2024swebench}. Defects4J provides real Java defects together with tests for repair studies~\cite{just2014defects4j}. \benchmark focuses on executable relationships between methods and on the evidence returned for each reachability decision.

\subsection{Runtime Behavior and Dependencies}

Other benchmarks examine more specific properties of program behavior. CRUXEval predicts inputs or outputs for short Python functions, and REval evaluates predictions about runtime behavior and intermediate states~\cite{gu2024cruxeval,chen2025reval}. Xie et al.'s CoRE evaluates static data and control dependencies and information flow, while Gao et al.'s CoRE tests implementation invariance and predictions about intermediate execution states~\cite{xie2025core,gao2026core}. SemBench includes function reachability, defined by connectivity in a static call graph over real-world C programs~\cite{xu2026semb}. TraceEval instead asks models to recover runtime call structures from repository-derived programs, with edges verified through execution~\cite{li2026traceeval}. CABRA also uses generated call-graph transformations to control task difficulty, but evaluates code-editing tasks with coding agents~\cite{balepur2026cabra}. \benchmark asks whether a target method executes from a selected source under the concrete values supplied during a generated execution. This differs from static function reachability because a visible call may be disabled by a false guard, and from runtime call-structure recovery because the task concerns one source--target question rather than reconstructing the full graph. A configurable algorithm controls method structure and value propagation, while the final dataset contains the generated classes, questions, labels, and executable-graph oracles. On this dataset, the evaluator scores the answer and exploration trace separately: a positive trace must show an executable route, while a negative trace must cover the full source-reachable region. The trace may use any valid exploration order. These choices support comparisons across factors such as \path{n_if}, \path{n_params}, and \path{class_size}, while covering a narrower range of Java behavior than repository-derived corpora.

\subsection{Reachability and Call-Graph Analysis}

Call-graph analysis studies the relationships needed to determine possible calls~\cite{grove2001framework,tip2000scalable}. In our tasks, reachability concerns the calls that can execute under a fixed invocation context. \benchmark uses this graph representation to check the relationships identified by the model, including visible calls disabled by conditions and methods omitted from the source-reachable region.
