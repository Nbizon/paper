\section{Background}
\label{sec:background}

Benchmarks turn broad model capabilities into measurable tasks. They define a set of problems, an expected output, and a metric used to compare systems. The choice of task and metric determines which aspects of model behavior can be observed. For program understanding, a useful distinction is between producing the correct result and providing evidence that is compatible with the program.

\subsection{Method Reachability}

Reachability is a standard problem in program analysis. In a call graph, methods are represented as nodes and calls as directed edges. A target method is reachable from a source method when a path exists between them. Call-graph construction has been studied through different analyses of the relationships between program elements~\cite{grove2001framework,tip2000scalable}.

\vspace{0.2cm}

For the programs considered here, a call can be visible in the source code without being executable. A condition may prevent it from running, and the value tested by that condition may come from another method. Following the visible calls is therefore insufficient to answer a condition-aware question. The model must also connect the values passed between methods with the conditions that use them.

\vspace{0.2cm}

The evidence required by a reachability question depends on its answer. For a reachable target, an executable route from the source establishes reachability. For an unreachable target, the exploration must account for the entire region executable from the source. The two polarities thus place different demands on the returned trace, even when their nominal generation distance is the same.

\subsection{Decisions and Observable Evidence}

The construction algorithm generates a call graph before constructing the corresponding Java code. This makes it possible to associate each question with an expected Boolean answer and an executable-graph oracle. The model returns a final answer and an ordered trace of explored methods, which are scored independently against this oracle.

\vspace{0.2cm}

The trace provides an additional observable signal beyond the final decision. For example, an answer may be correct even though its trace omits a required method or includes a call whose condition is false. Comparing the returned methods with the executable graph makes these defects detectable. However, the trace is itself generated output and may differ from the process used to produce the answer. It therefore supports analysis of the model's evidence, without providing direct access to its internal reasoning.
