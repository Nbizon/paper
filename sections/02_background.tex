\section{Background}
\label{sec:background}

\subsection{Method Reachability and Execution Context}

A method-reachability question asks whether a target method can be invoked through direct or indirect calls from a source method. This relationship can be represented using a call graph, where methods are nodes and calls are directed edges. The target is reachable from the source when a path connects them. Different analyses have been proposed to construct these graphs from the relationships between program elements~\cite{grove2001framework,tip2000scalable}.

However, a call can be visible in the source code without being executed. It may appear inside a condition that is false, so following all visible calls does not necessarily describe what happens during execution. Determining reachability then requires examining both the calls between methods and the values that decide whether these calls execute.

These values depend on the execution context, which includes the supplied arguments and initial state. For a deterministic program, fixing this context determines which branches are taken and which methods are invoked. When a condition depends on a parameter, evaluating it may require following a value passed through several methods. As a consequence, the declaration of the queried source method alone may not provide enough information to answer the question. The tasks considered here use reachability under this given execution context.

\subsection{Decisions and Executable Evidence}

A Boolean answer indicates whether the target is reachable, but does not describe the calls supporting that decision. Establishing reachability requires finding an executable route to the target, while establishing unreachability requires ruling out all such routes. The evidence needed to support the answer therefore depends on the question's polarity.

We use the term \emph{trace} to refer to the ordered exploration of methods returned by the model alongside its answer. This exploration need not reproduce every invocation or follow one chronological execution sequence: independent branches can be explored in different orders. Its purpose is to provide evidence that can be checked against the executable calls in the program.

A correct answer does not necessarily mean that this evidence is valid. In Figure~\ref{fig:background-example}, a model can correctly state that \texttt{sortJobForRequest} is unreachable from \texttt{buildSessionToBuffer}, while including it in the trace through the call guarded by a false condition. Evaluating the answer and trace separately allows us to distinguish these cases.

Since the trace is itself generated, it does not give direct access to the model's internal reasoning. It provides an additional observable output whose compatibility with the program can be evaluated. Section~\ref{subsec:scoring} gives the rules used to check this output independently of the Boolean answer.
