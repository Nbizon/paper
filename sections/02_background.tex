\section{Related Work}
\label{sec:background}
\label{sec:related-work}

\subsection{Evaluating Whether a Model Can Complete a Task}

Most benchmarks for code-oriented LLMs evaluate whether a model can produce a correct final result. HumanEval, MBPP, and APPS ask models to generate functions or solve programming problems, and use tests to verify the generated code~\cite{chen2021codex,austin2021program,hendrycks2021apps}. CodeXGLUE extends this evaluation to several code-understanding and code-generation tasks~\cite{lu2021codexglue}. LiveCodeBench uses recent programming problems, while BigCodeBench introduces tasks that require a larger use of libraries and APIs~\cite{jain2024livecodebench,zhuo2024bigcodebench}.

Other benchmarks move closer to the work performed by developers. SWE-bench asks models to solve real GitHub issues at the repository level~\cite{jimenez2024swebench}. Defects4J was not introduced as an LLM benchmark, but its collection of Java defects and tests is widely used to evaluate program repair~\cite{just2014defects4j}. These benchmarks are useful because they show whether a model can complete a realistic task. However, a successful result can depend on several capabilities at the same time, such as finding the relevant file, understanding an API, modifying the code, and using test feedback. They therefore provide limited information about the specific part of the task that caused a failure.

\subsection{Evaluating How a Model Understands a Program}

Several benchmarks reduce the scope of the task to study program behavior more directly. CRUXEval asks models to infer the input or output of short Python functions~\cite{gu2024cruxeval}. REval evaluates runtime properties such as execution paths, coverage, program state, and output~\cite{chen2024reval}. CORE provides tasks based on data dependencies, control dependencies, and information flow in several languages~\cite{xie2025core}. TraceEval uses execution-verified problems to evaluate semantic reasoning and runtime call structure~\cite{li2026traceeval}. Finally, RE2-Bench studies code reasoning in real-world settings and shows the importance of relating controlled evaluations to realistic programs~\cite{liu2025re2bench}.

These benchmarks make program behavior more observable, but they do not all have the same objective. Some evaluate the prediction of a program state or output, while others evaluate several analysis tasks together. \benchmark focuses only on reachability between methods. This narrower scope allows us to modify the structure of the program while keeping the question and the expected output unchanged.

\subsection{Position of \benchmark}

Reachability is a standard problem in program analysis. A call graph represents methods as nodes and possible calls as directed edges. A target method is reachable from a source method when a path connects the two nodes. Static and dynamic analyses have used this representation for many years~\cite{grove2001framework,tip2000scalable}. \benchmark does not propose an LLM as an alternative to these tools. It uses reachability because the task has an exact answer while still requiring the model to connect information distributed across several methods.

The main difference of \benchmark comes from the way the programs are created. The benchmark generates the call graph before generating the Java code. It therefore knows which methods are connected, which calls can execute, and which sequence of methods is expected for each question. It can also change one factor, such as trace length or class size, without changing the nature of the task.

This known structure also makes it possible to request a trace in addition to the final answer. The trace is not considered a direct representation of the model's internal reasoning. It is a generated output that can contain its own errors. However, it provides information that is absent from a Boolean answer. A model can return the correct answer while skipping a method, following an impossible transition, or using a call that is visible in the code but cannot execute. \benchmark uses the oracle graph to distinguish these cases automatically.
