\subsection{Code Generation and Software-Engineering Benchmarks}

Benchmarks for code-oriented LLMs cover many different tasks. HumanEval, MBPP, and APPS ask models to generate functions or solve programming problems, and use tests to check the generated code~\cite{chen2021codex,austin2021program,hendrycks2021apps}. CodeXGLUE combines several datasets for code understanding and code generation~\cite{lu2021codexglue}. At the repository level, SWE-bench asks models to produce patches for real GitHub issues~\cite{jimenez2024swebench}. LiveCodeBench uses recent programming problems, while BigCodeBench studies code generation with a larger use of libraries and APIs~\cite{jain2024livecodebench,zhuo2024bigcodebench}. Defects4J was not designed as an LLM benchmark, but it provides Java defects and testing tools that are widely used in program-repair experiments~\cite{just2014defects4j}.

These benchmarks are useful because they measure whether a model can complete a task that is relevant to software engineering. However, completing such a task can require several capabilities, including problem decomposition, API knowledge, dependency handling, code editing, and the use of test feedback. \benchmark has a different objective. It fixes the form of the programs and questions so that structural factors can be varied separately and their effects can be observed more directly.

\subsection{Benchmarks for Program Behavior and Code Reasoning}

Other benchmarks focus more directly on program behavior. CRUXEval asks models to predict the input or output of short Python functions~\cite{gu2024cruxeval}. REval evaluates properties such as execution paths, coverage, program state, and output~\cite{chen2024reval}. CORE provides static-analysis tasks related to data dependencies, control dependencies, and information flow in several languages~\cite{xie2025core}. TraceEval is close to our work because it uses execution-verified tasks to study semantic reasoning and runtime call structure across several languages~\cite{li2026traceeval}. RE2-Bench studies code reasoning in real-world settings and highlights the importance of connecting synthetic tasks with realistic programs~\cite{liu2025re2bench}.

\benchmark makes a more restricted choice. It uses generated Java programs so that trace length, class size, query polarity, and guarded calls can be controlled while keeping an exact oracle. This restriction makes the benchmark less realistic than repository-level evaluations, but it also makes errors easier to analyze. When performance changes, we know which structural factor was modified. \benchmark is therefore complementary to benchmarks based on real programs.

\subsection{Reachability in Program Analysis}

Reachability is a common problem in program analysis. In a call graph, methods are represented by nodes and possible calls are represented by directed edges. A target method is reachable from a source method when a path connects the two nodes. Static and dynamic analyses have used call graphs and reachability for many years to study software behavior~\cite{grove2001framework,tip2000scalable}. For the analysis of real deployed software, existing program-analysis tools remain more appropriate than LLMs.

In \benchmark, reachability is used as an evaluation task. The generated programs provide controlled experimental objects for which the complete graph is known. The generator records the intended call graph, the validator checks that it is correctly represented in the Java program, and the evaluator compares model outputs with the resulting labels and traces. The objective is therefore to study how LLMs reason about program structure, not to replace existing analysis tools.

\subsection{Traces as Diagnostic Outputs}

A Boolean answer indicates whether the final decision is correct, but it does not show how the model followed the program structure. For this reason, we also ask the model to return an ordered sequence of methods. This trace is an output generated by the model and should not be interpreted as direct access to its internal reasoning. It can contain generation or formatting errors, and it can also be produced after the model has already selected its final answer.

Despite this limitation, the trace provides additional information. Two models can obtain the same final-answer accuracy while producing different traces. One model may reproduce the executable order, another may omit intermediate calls, and another may follow a call that is present in the source but cannot be executed. These behaviors cannot be distinguished from the Boolean answer alone.

We use several metrics to capture these differences. Exact trace accuracy checks whether the complete predicted trace is equal to the oracle trace. Trace completeness measures how much of the oracle sequence is recovered in the correct order. Graph-valid exploration checks whether each transition is present in the executable graph. Finally, syntactic-call bias identifies calls that are visible in the source but absent from the executable graph. Together, these metrics provide a more detailed analysis of model success and failure.
