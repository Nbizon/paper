\section{Background}
\label{sec:background}

\subsection{Method Reachability and Execution Context}

Reachability is a standard problem in program analysis. In a call graph, methods are represented as nodes and calls as directed edges. A target method is reachable from a source method when a path connects them through direct or indirect calls. Different analyses have been proposed to construct these graphs from the relationships between program elements~\cite{grove2001framework,tip2000scalable}.

However, a call can be visible in the source code without being executable. It may appear inside a condition that is false, and the value tested by that condition may come from another method. Following all visible calls therefore does not necessarily describe what happens during execution. For the tasks considered here, reachability is defined using the calls that can execute under the given execution context.

This context includes the argument values and initial state needed to answer the question. In a deterministic program, these values determine which branches are taken and which methods are invoked. When a condition depends on a parameter, evaluating it may require following the value through several methods. The declaration of the queried source method alone may therefore not provide enough information to determine reachability.

Figure~\ref{fig:background-example} illustrates this with a complete four-method program produced by the construction algorithm. \texttt{Main} invokes \texttt{copySessionFromFile}, a root method with no parameters, which initializes \texttt{message} to 4. This value is passed to \texttt{buildSessionToBuffer} and then to \texttt{clearNotificationFromUrl}. Both conditions comparing the value with $-5$ are false. As a consequence, only \texttt{clearNotificationFromUrl} is reached from \texttt{buildSessionToBuffer}. The method \texttt{sortJobForRequest} executes through a separate call from the root, but is not reachable from the source named in the question. The answer therefore depends on the calls made from this source with its supplied arguments, rather than on whether the target executes elsewhere in the program.

\subsection{Decisions and Executable Evidence}

A reachability decision indicates whether the target can be reached from the source. For a reachable target, following an executable route from the source is enough to establish reachability. For an unreachable target, our evaluation instead requires the model to explore the complete region executable from the source and exclude the target. Positive and negative questions therefore require different amounts of supporting evidence.

We use the term \emph{trace} to refer to the ordered exploration of methods returned by the model. It contains explored methods rather than every invocation made during execution. Independent branches can be explored in different orders, provided that each new method is introduced through an executable call from an earlier method. The oracle therefore checks whether the trace is compatible with the program, without requiring one chronological execution sequence.

A correct answer does not necessarily mean that the trace is valid. In Figure~\ref{fig:background-example}, a model can correctly state that \texttt{sortJobForRequest} is unreachable from \texttt{buildSessionToBuffer}, while including it in the trace or omitting \texttt{clearNotificationFromUrl}. By evaluating the decision and trace separately, we can identify these differences.

The trace is itself generated by the model, so it does not give direct access to its internal reasoning. It nevertheless allows us to check the evidence provided for the answer. The next sections explain how the executable-graph oracle is constructed and how the returned traces are evaluated.
