\subsection{Code Generation and SE Benchmarks}

Code benchmarks for LLMs span from function-level synthesis to repository-level software-engineering tasks. HumanEval, MBPP, and APPS evaluate whether models can synthesize code that satisfies executable tests or programming-problem specifications~\cite{chen2021codex,austin2021program,hendrycks2021apps}. CodeXGLUE collects code-understanding and code-generation tasks across multiple datasets~\cite{lu2021codexglue}. SWE-bench shifts the unit of evaluation to real GitHub issues and repository patches~\cite{jimenez2024swebench}. LiveCodeBench and BigCodeBench broaden code-generation evaluation with newer programming problems and more complex library-using tasks~\cite{jain2024livecodebench,zhuo2024bigcodebench}. Defects4J is not primarily an LLM benchmark, but it remains an important Java bug corpus and testing infrastructure for controlled repair studies~\cite{just2014defects4j}.

These benchmarks are central for measuring task success, but they intentionally combine many abilities. A benchmark score may reflect problem decomposition, API recall, test use, patch editing, dependency handling, or local structural reasoning. \benchmark makes a complementary trade-off. It narrows the program form and query schema to isolate executable inter-method reachability, so that failures can be analyzed by controlled structural factors rather than only by aggregate task success.

\subsection{Program Behavior and Code Reasoning Benchmarks}

Several benchmarks move closer to program behavior and semantic structure. CRUXEval asks models to infer inputs or outputs for short Python functions~\cite{gu2024cruxeval}. REval studies runtime behavior such as coverage, paths, state, and output~\cite{chen2024reval}. CORE evaluates static-analysis-oriented reasoning tasks including data dependency, control dependency, and information flow across multiple languages~\cite{xie2025core}. TraceEval is especially close in spirit because it evaluates execution-verified semantic reasoning and runtime call structure across languages~\cite{li2026traceeval}. RE2-Bench highlights the importance of testing code reasoning in real-world settings and cautions against treating synthetic tasks as substitutes for real-program evaluation~\cite{liu2025re2bench}.

\benchmark differs in the experimental control it seeks. It deliberately uses a narrower Java setting to obtain oracle-supervised control over canonical trace length, class size, polarity, and guards. This choice does not make realistic benchmarks less important; instead, it makes a different measurement possible. The benchmark asks whether a model can recover a validated executable call relation and a specified trace convention when confounding factors are minimized.

\subsection{Reachability and Program Analysis}

Reachability is a foundational notion in program analysis. In a call graph, nodes represent methods and directed edges represent possible calls; method reachability asks whether a target method can be reached from a source by following those edges. Call-graph construction and reachability analysis have long been studied in static and dynamic analysis~\cite{grove2001framework,tip2000scalable}, and mature analysis tools are the right mechanism when the goal is to answer reachability questions for deployed software.

\benchmark uses reachability differently. The benchmark is not a proposal to replace program analysis with LLMs. It uses generated programs as controlled experimental instruments: the generator defines the intended executable graphs, the validator checks that the Java source realizes it, and the evaluator compares model outputs against oracle labels and traces. This makes reachability useful as a diagnostic substrate for studying structural reasoning under exact supervision.

\subsection{Trace Outputs and Diagnostic Evaluation}

Trace outputs provide a way to evaluate more than the final Boolean answer. In \benchmark, a trace is not treated as direct evidence of a model's hidden reasoning process; rather, it is an externally checkable output artifact. Although the path followed internally by the model during reasoning is likely to be strongly correlated with the trace it reports, the two should not be assumed to be exactly identical. The reported trace may reflect the model's structural understanding of the problem, but it may also be affected by generation errors, post-hoc rationalization, or formatting constraints.

This distinction motivates our use of traces as diagnostic artifacts rather than explanations of internal cognition. In particular, traces allow us to assess whether the model is able, in its final answer, to reconstruct the actual execution path in the code. Thus, the evaluation captures not only whether the model predicts the correct Boolean outcome, but also whether it can explicitly recover the executable structure that leads to that outcome.

This is important because two models with the same final-answer accuracy may exhibit different structural behavior: one may follow executable edges in the canonical order, another may skip intermediate calls, and another may follow a syntactically visible call that cannot execute.

The trace requirement turns these differences into measurable outcomes. Exact canonical trace accuracy tests adherence to the oracle convention, trace completeness measures how much of the oracle exploration is recovered, graph-valid exploration checks whether reported transitions exist in the executable graph, and syntactic-call bias detects confusion between visible and executable calls. This diagnostic evaluation complements end-to-end task benchmarks by making structural failure modes explicit.
