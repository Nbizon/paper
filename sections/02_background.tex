\section{Background and Related Work}
\label{sec:background}

\subsection{Code and Software-Engineering Benchmarks}

LLM evaluation for code has largely been shaped by benchmarks that test whether a system can produce useful code or solve realistic software-engineering tasks. HumanEval, MBPP, and APPS evaluate function-level or programming-problem synthesis with executable tests~\cite{chen2021codex,austin2021program,hendrycks2021apps}. CodeXGLUE collects code-understanding and code-generation tasks across multiple datasets~\cite{lu2021codexglue}. More recent benchmarks broaden the setting: SWE-bench evaluates repository-level issue resolution from real GitHub issues~\cite{jimenez2024swebench}, while LiveCodeBench and BigCodeBench emphasize newer programming problems and more complex library-using generation tasks~\cite{jain2024livecodebench,zhuo2024bigcodebench}. Defects4J provides a reproducible Java bug and testing infrastructure that is often used in program-repair research, although it is not primarily an LLM benchmark~\cite{just2014defects4j}.

These benchmarks are the right place to measure end-to-end usefulness, but they are less suited to isolating one structural capability. A failed patch may reflect poor localization, weak API knowledge, insufficient context use, brittle editing, or a misunderstanding of program structure. \benchmark makes the complementary trade-off: it fixes the source-program form, query schema, and trace convention so that failures can be related to controlled structural factors.

\subsection{Code Reasoning and Semantic-Structure Benchmarks}

Several benchmarks move closer to the structure of program behavior. CRUXEval asks models to predict inputs or outputs for short Python functions~\cite{gu2024cruxeval}. REval evaluates runtime behavior, including coverage, paths, state, and output~\cite{chen2024reval}. CORE studies static-analysis tasks such as data dependency, control dependency, and information flow across C/C++, Java, and Python~\cite{xie2025core}. TraceEval is especially relevant because it asks models to recover runtime call structure from execution-verified programs across multiple languages~\cite{li2026traceeval}. RE2-Bench provides an important caution for this line of work: synthetic code-reasoning tasks can underrepresent real-world complexity and should not be treated as a substitute for real-program evaluation~\cite{liu2025re2bench}.

\benchmark occupies a deliberately narrower point in this design space. It gives direct control over canonical distance, class size, query polarity, and condition-aware guards, at the cost of using generated single-class programs rather than real projects. That control is difficult to obtain from real repositories, where naming, architecture, task difficulty, tests, and execution behavior are naturally entangled. TraceEval is more ecological but less parameterized; CORE is broader but not centered on one executable-reachability task; and CRUXEval and REval focus on execution behavior without the same Java inter-method factorization.

\subsection{Reachability and Program Analysis}

Reachability is a standard notion in program analysis. In a call graph, nodes represent methods and directed edges represent possible calls. A method-reachability query asks whether a target method can be reached from a source method by following those edges. Call-graph construction and reachability analysis have been studied for decades~\cite{grove2001framework,tip2000scalable}, and mature analysis tools are usually the right mechanism when the goal is to answer such queries in deployed software.

In \benchmark, reachability is the controlled substrate for evaluation rather than the end-user problem being solved. The generated call graph provides the oracle and the validation mechanism: each program has known executable edges, labels, and canonical traces. This lets the evaluation separate cases that would otherwise be collapsed into a single answer, including valid paths, shortcuts, non-existent edges, missing intermediate methods, and calls that are visible in the source but disabled by generated conditions.

\subsection{Trace Outputs and Evaluation}

\benchmark asks for a trace in addition to the Boolean answer. The trace is not treated as evidence of hidden cognition; it is an observable output artifact that can be checked against the executable graph. A model that answers correctly but emits an invalid transition is different from a model that follows the graph but stops early, and both are different from a model that confuses syntactic call presence with executable reachability.
