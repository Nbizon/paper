\section{Background}
\label{sec:background}

\subsection{Method Reachability and Execution Context}

Reachability is a standard problem in program analysis. In a call graph, methods are represented as nodes and calls as directed edges. A target method is reachable from a source method when a path connects them through direct or indirect calls. Call-graph construction has been studied through different analyses of the relationships between program elements~\cite{grove2001framework,tip2000scalable}.

\vspace{0.2cm}

However, a call can be visible in the source code without being executable. A condition may prevent it from running, and the value tested by that condition may come from another method. A graph containing all visible calls therefore does not necessarily describe the calls executed in a particular execution. For the tasks considered here, reachability is defined over the executable calls under the given execution context.

This context includes the argument values and initial state relevant to the question. In a deterministic program, these values determine which branches are taken and which methods are invoked. When a condition reads a parameter, understanding whether its guarded call executes can require following the value through several methods. The declaration of the queried source method alone may therefore be insufficient to determine reachability.

class Example {
    public static void main(String[] args) {
        source(0);
    }
    static void source(int x) {
        if (x > 0) target();
        other();
    }
    static void target() {}
    static void other() {}
}
\end{verbatim}
\end{minipage}
\caption{A class containing several methods. The entry point fixes the value received by \texttt{source}: \texttt{other} executes, whereas the visible call to \texttt{target} does not.}
\label{fig:background-example}
\end{figure}

Figure~\ref{fig:background-example} illustrates this distinction in a class containing several methods. The \texttt{main} method invokes \texttt{source} with the value zero. The call to \texttt{target} is visible in \texttt{source}, but its condition is false, so the target is not reached. The call to \texttt{other} executes unconditionally. If \texttt{source} instead received a positive value, \texttt{target} would also execute. The reachability decision thus depends on both the calls present in the class and the context supplying their values.

\vspace{0.2cm}

In the deterministic programs considered in this study, the entry point and assignments fix the values needed to evaluate execution. The task is to determine which calls execute under this context, rather than whether a target could be called for some other input. Section~\ref{sec:benchmark-design} describes how this context is represented in the generated instances and supplied to the model.

\subsection{Decisions and Executable Evidence}

A reachability decision indicates whether the target can be reached from the source. The evidence needed to support this decision depends on its answer. For a reachable target, an executable route from the source establishes reachability. In our evaluation, an unreachable-target response must instead account for the complete region executable from the source and exclude the target. Positive and negative questions therefore place different demands on the returned evidence.

\vspace{0.2cm}

We use the term \emph{trace} for an ordered exploration of methods serving as this evidence. It records explored methods rather than every runtime invocation. Independent branches may be explored in different orders, provided that the method introductions are supported by executable calls. The trace is therefore checked for compatibility with the program, without requiring one chronological execution sequence.

A correct decision does not necessarily come with a valid trace. In Figure~\ref{fig:background-example}, a response can correctly state that \texttt{target} is unreachable while incorrectly including it in the exploration or omitting \texttt{other}. Evaluating the decision and trace separately makes these differences visible.

\vspace{0.2cm}

The trace is itself generated output and may differ from the process used to produce the answer. It provides an observable signal for examining the model's evidence, without giving direct access to its internal reasoning. The construction of the executable-graph oracle and the precise scoring rules are described in the next sections.
