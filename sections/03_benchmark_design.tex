\section{Benchmark Design}
\label{sec:benchmark-design}

\benchmark is a software-engineering benchmark artifact. The dataset is not meant to mimic every feature of production Java systems. Its role is narrower: create a setting where program-flow complexity can be varied and measured. The generator exposes graph family, graph size, source-target depth, code-level stressors, and requested reasoning budget as explicit experimental factors. The current paper reports a fully quantified control-flow study and specifies the paired data-flow study supported by the same generation principles.

\subsection{Task Definition}

\textbf{Control-flow input:} a Java class and a natural-language question of the form: \emph{Does method A call method B, either directly or indirectly?}

\textbf{Data-flow input:} a Java class and a natural-language question that asks whether a value introduced at one program point can influence a later value, parameter, return expression, or call argument. Data-flow instances reuse the generator's method graph but make variables, parameters, assignments, and call arguments semantic rather than merely distracting.

\textbf{Output:} a JSON object with:
\begin{itemize}[leftmargin=*]
    \item \texttt{trace}: ordered list of method names or data-flow program points;
    \item \texttt{final\_answer}: \true or \false.
\end{itemize}

\textbf{Oracle:} generated graph metadata and validation from the analysis pipeline. For control-flow questions, the oracle is the source-target call path or the absence of such a path. For data-flow questions, the oracle is the generated value-dependency path.

\subsection{Dataset Generation Pipeline}

Dataset generation has three stages. The generator first samples unique method names and builds an abstract flow structure. It then materializes that structure as Java code, optionally adding comments, local variables, parameters, loops, and conditionals. Finally, it samples questions and writes the oracle files consumed by the evaluation scripts.

The pipeline currently supports two complementary call-graph families:
\begin{itemize}[leftmargin=*]
    \item \textbf{Linear graphs} isolate path-following behavior. The relevant structure is a chain of method calls, which separates the effect of depth from the effect of branching.
    \item \textbf{Tree graphs} add branching and negative reasoning. A source method may call multiple descendants, and unreachable targets force the model to avoid treating code co-occurrence as reachability. These cases are closer to the exploration used in call-graph comprehension.
\end{itemize}

The implementation makes the following design choices:
\begin{itemize}[leftmargin=*]
    \item The benchmark language is Java.
    \item Method names sampled from realistic camelCase verb/noun fragments.
    \item Method bodies are shuffled in the class to prevent position-only solutions.
    \item Positive and negative questions sampled per depth, so reachable and unreachable decisions can be studied separately.
    \item Stored artifacts for each case: generated class, prompt, reachability questions, oracle chains, method list, and configuration metadata.
\end{itemize}

\subsection{Generated Call-Graph Structures}

Each generated Java class is the textual representation of an underlying directed call graph. Nodes correspond to methods, and directed edges correspond to method calls. Reachability questions are asked over this graph, not over the textual order of methods in the file. That distinction matters because method bodies are shuffled before the class is written: a method can appear late in the file while sitting close to the root of the call graph, or the reverse. Solving the task requires reconstructing call relations from code.

\subsubsection{Linear Structure}

In the linear configuration, the generator builds one or more method chains. Within a chain, method $m_i$ calls only its successor $m_{i+1}$; the last method has no outgoing call. The graph is a directed path:
\[
    m_1 \rightarrow m_2 \rightarrow \cdots \rightarrow m_k.
\]
Position in the chain determines reachability. A question $(m_i, m_j)$ is positive when $i < j$, because execution can follow successor edges from $m_i$ to $m_j$. A question is negative when the target is upstream or outside the suffix reachable from the source. For example, $m_2$ reaches $m_5$, but $m_4$ does not reach $m_2$ because calls never go backward. Linear cases isolate path length: increasing the source-target distance increases the number of method definitions the model has to connect, without adding branches.

\subsubsection{Tree Structure}

In the tree configuration, the generator builds a rooted directed tree. Each method can call its children; leaves have no outgoing call. A target is reachable from a source exactly when it lies in the source's descendant subtree. In \figpanelref{fig:generated-call-graphs}{(b)}, $u_0$ reaches every node in the fragment, while $R(u_0)$ does not reach $R(L(u_0))$ because that target belongs to a sibling subtree.

Tree instances introduce two difficulties absent from linear chains. A model has to follow multiple outgoing calls from the same method. Negative examples also require branch-sensitive reasoning: the target method may appear in the same Java class, even close by in the textual file, while remaining unreachable from the queried source. For that reason, tree cases better resemble common comprehension tasks such as impact analysis, security reachability checks, and debugging through call hierarchies.

Tree generation uses breadth-first construction with a probabilistic local expansion rule. Let $u$ be the node currently processed, and let $L(u)$ and $R(u)$ denote its left and right children. When enough method names remain, both children are created:
\[
    u \rightarrow L(u), \qquad u \rightarrow R(u).
\]
The left child may then be expanded one level further. Two independent Bernoulli variables control that expansion:
\[
    X_{LL}(u) \sim \mathrm{Bernoulli}(p),
    \qquad
    X_{LR}(u) \sim \mathrm{Bernoulli}(p).
\]
\figref{fig:local-tree-rule} shows the local rule. Children $L(u)$ and $R(u)$ form the deterministic skeleton, while the two descendants of $L(u)$ are sampled independently.

If $X_{LL}(u)=1$, the generator creates the left child of the left child, $L(L(u))$. If $X_{LR}(u)=1$, it creates the right child of the left child, $R(L(u))$:
\[
    \begin{aligned}
    X_{LL}(u)=1 &\Rightarrow L(u) \rightarrow L(L(u)),\\
    X_{LR}(u)=1 &\Rightarrow L(u) \rightarrow R(L(u)).
    \end{aligned}
\]
The active tree generator currently uses $p=0.65$ by default.

The rule gives a simple distribution for the local shape below $L(u)$. The probability that the left child remains a leaf is
\[
    \Pr(\mathrm{outdeg}(L(u)) = 0) = (1-p)^2.
\]
The probability that it has exactly one child is
\[
    \Pr(\mathrm{outdeg}(L(u)) = 1) = 2p(1-p),
\]
and the probability that it has two children is
\[
    \Pr(\mathrm{outdeg}(L(u)) = 2) = p^2.
\]
Equivalently, the expected number of extra children attached under $L(u)$ is
\[
    \mathbb{E}[\mathrm{outdeg}(L(u))] = \mathbb{E}[X_{LL}(u)+X_{LR}(u)] = 2p.
\]
Larger values of $p$ increase the local branching factor and produce broader subtrees around left branches.

The extreme cases make the parameter's role concrete. If $p=0$, then $X_{LL}(u)=X_{LR}(u)=0$ for every processed node. The generator still creates $L(u)$ and $R(u)$, but $L(u)$ remains a leaf. Because the right child is systematically queued for later expansion, the global structure approaches a right spine with one left leaf attached at each processed node. This case emphasizes long reachability paths with limited branching. If $p=1$, then $X_{LL}(u)=X_{LR}(u)=1$ for every processed node. Every generated left child is immediately expanded into a binary node, making the structure denser for a fixed number of methods. The number of sibling subtrees increases as well, creating more negative reachability pairs where the target exists in the same class but lies outside the source subtree.

For a finite context size $N$, the process stops when the generated method-name list is exhausted. The equations above describe the local generation rule before exhaustion; the final levels may be truncated when fewer method names remain. For this reason, \benchmark stores the realized tree and derives questions from that graph, rather than from the probability model alone.

\subsubsection{From Graph to Java Code}

After constructing the abstract graph, the generator emits one Java method per node. For an edge $u \rightarrow v$, the body of method $u$ contains a call to method $v$. Depending on the configuration, method bodies may also contain comments, local variables, loops, conditionals, and parameters. These elements vary the surface complexity of the code while preserving the reachability relation. The final method order in \texttt{TheClass.java} is randomized, so the benchmark measures call-graph reconstruction rather than reading order.

\subsection{Prompting Protocol}

All models receive the same task framing for a given experiment family. The prompt defines the required JSON schema, states that the trace must list the methods or program points that justify the answer, and includes the generated Java class and the natural-language query. The control-flow prompt asks the model to reason over direct and indirect method calls. The data-flow prompt uses the same response schema but asks the model to follow value dependencies through assignments, parameters, return values, and call arguments. In both families, the evaluator treats invalid JSON, missing fields, and unparsable traces as incorrect for trace metrics while still attempting to recover a final Boolean answer when it can be extracted unambiguously.

\subsection{Benchmark Outputs and Metadata}

Each generated case is stored as a small directory whose files are sufficient to reproduce the prompt and the oracle:
\begin{itemize}[leftmargin=*]
    \item \texttt{TheClass.java}: generated source program.
    \item \texttt{system.txt}: task instructions plus source code.
    \item \texttt{reachability\_questions.txt}: one question per line, prefixed by signed distance.
    \item \texttt{chains.txt}: expected trace/chain aligned by question index.
    \item \texttt{methods.txt}: generated method names.
    \item \texttt{config.json}: context size, depth range, comments, variables, loops, conditionals, parameters.
\end{itemize}
