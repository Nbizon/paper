\subsection{Task Definition}

Each benchmark instance contains a generated Java class, a source method, a target method, and a question: does the source method call the target method directly or indirectly? The model must return a JSON object with two fields: \texttt{final\_answer}, a Boolean reachability label, and \texttt{trace}, an ordered list of method names.

Control-flow reachability and condition-aware reachability share this question and output schema. In control-flow reachability, method calls are placed outside control-flow structures; calls are not guarded by \texttt{if}, \texttt{for}, \texttt{while}, or other constructs; every generated method call is active for reachability. Variables, comments, loops, and other code-surface elements may exist only if they do not affect method-call reachability.

In condition-aware reachability, method calls may remain outside control-flow structures or appear inside \texttt{if} statements. Calls inside branches whose conditions evaluate to false are visible in the source code but are not executable. The model must therefore distinguish syntactic call presence from executable reachability. Calls are not guarded by loops in the final task definition.

\subsection{Syntactic and Executable Call Graphs}

Condition-aware reachability separates two graphs. The \emph{syntactic call graph} contains all method calls visible in the Java source code, including calls inside non-passing \texttt{if} branches. The \emph{executable call graph} contains only calls that are actually executed under the generated variable values and conditions. A guarded call may therefore belong to the syntactic call graph while being absent from the executable call graph used by the oracle.

This distinction creates a characteristic error mode: \emph{syntactic-call bias}. A model exhibits syntactic-call bias when it treats a visible method call as evidence of reachability even though the call is inside a non-executed branch and is absent from the executable call graph.

\subsection{Tree-Shaped Graph Generation}

The final benchmark focuses on tree-shaped call graphs generated from randomized pseudo-binary trees. Nodes correspond to Java methods, directed edges correspond to method calls, and generated graphs are acyclic. The current benchmark does not include inheritance, interfaces, dynamic dispatch, overloading, exceptions, recursion, external libraries, or multi-class projects.

The generator starts from an ordered tree. It preserves child order when materializing method bodies, so the order of call statements inside each generated Java method is code-aligned with the ordered abstract graph. The declarations of methods inside the generated class are shuffled to prevent models from exploiting declaration order. Method order shuffling is part of the benchmark design, not an experimental ablation.

\subsection{Canonical Execution-Oriented Trace}

The oracle trace is a canonical execution-oriented traversal trace. It is graph-defined and code-aligned. The generator creates an ordered tree-shaped call graph and materializes the order of children as the textual order of call statements inside each Java method body. Therefore, the oracle traversal follows the ordered call graph and the order in which calls appear in the generated Java code.

For positive queries, the final answer is \true, and the trace corresponds to the first execution-consistent exploration that reaches the target. The trace follows method calls in canonical execution-oriented order and is not necessarily the shortest source-target path. For negative queries, the final answer is \false, and the trace corresponds to the canonical execution-oriented exploration from the source until the reachable region has been exhausted without reaching the target.

For condition-aware instances, the canonical trace follows the executable call graph. Calls in false \texttt{if} branches are excluded from the canonical trace, even if they are syntactically present in the source code.

\subsection{Signed Canonical Distance}

The main distance is canonical execution-trace distance, not shortest-path distance in the abstract graph. For positive queries, distance is the number of execution-consistent traversal steps required to reach the target from the source. For negative queries, distance is defined over the canonical exploration performed from the source before concluding that the target is unreachable. Distances are signed: $+d$ for positive queries and $-d$ for negative queries. We use absolute canonical distance or target distance level for $d \in \{1,\ldots,25\}$.

\subsection{Dataset Configuration}

The final planned dataset uses tree-shaped call graphs only, $p = 0.65$, context sizes 100, 250, and 500, absolute canonical distances 1 to 25, and positive and negative queries for each distance level. For each task family, the planned size is:
\[
\begin{aligned}
N ={}& \texttt{nb\_context} \times \texttt{nb\_if} \times \texttt{nb\_loop} \times \texttt{nb\_comment}\\
& \times \texttt{nb\_depths} \times \texttt{nb\_params} \times \texttt{nb\_vars} \times 2\\
& \times \texttt{nb\_questions\_per\_depth}.
\end{aligned}
\]
The factor 2 corresponds to positive and negative queries. The target design balances the two task families: $N_{control-flow} = N_{condition-aware}$. \redtodo{Confirm final value of \texttt{nb\_questions\_per\_depth}; current provisional value is 4.}

\subsection{Benchmark Outputs and Metadata}

Each generated case is stored in a directory containing the generated Java class, task prompt, reachability questions, oracle traces, method list, and configuration metadata. The metadata records context size, distance range, comments, variables, loops, conditionals, parameters, and task-family configuration.

\subsection{Oracle Validation}

We validate generated instances using a programmatic oracle-validation pipeline. This pipeline checks that the generated Java code compiles, that the materialized method calls match the intended tree-shaped call graph, and that sampled positive and negative queries agree with the reachability relation induced by the generated program. It also validates that oracle traces follow the benchmark's canonical execution-oriented traversal. For condition-aware instances, the validation additionally checks that generated variables and conditions correctly determine whether guarded calls are executed.
