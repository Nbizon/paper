\label{sec:benchmark-design}

\subsection{Task Definition}

An instance in \benchmark is a tuple
\[
    (P, s, t, f, y, \tau, m),
\]
where $P$ is a generated Java program, $s$ is the source method, $t$ is the target method, $f$ is the task family, $y$ is the executable reachability label, $\tau$ is the canonical trace, and $m$ is metadata describing controlled factors and oracle graph properties. The label $y$ is \true{} when execution starting in $s$ can reach $t$ through direct or indirect executable method calls, and \false{} otherwise.

Each prompt asks the model to return a JSON object with two fields:
\begin{itemize}[leftmargin=*]
    \item \texttt{final\_answer}: a Boolean reachability prediction;
    \item \texttt{trace}: an ordered list of method names interpreted under the benchmark's canonical trace convention.
\end{itemize}
The Boolean answer and trace are evaluated separately, so a correct final answer does not imply a correct explanation under the benchmark oracle.

\subsection{Syntactic and Executable Call Graphs}

For each generated program, \benchmark distinguishes a syntactic call graph $G_{\mathit{syn}}$ from an executable call graph $G_{\mathit{exec}}$. $G_{\mathit{syn}}$ contains all calls visible in the source text. $G_{\mathit{exec}}$ contains only calls that execute under the generated values and guard outcomes. In unguarded tasks, every generated visible call executes, so $G_{\mathit{syn}} = G_{\mathit{exec}}$. In condition-aware tasks, calls may be visible inside false generated guards, so $G_{\mathit{exec}}$ is a subgraph of $G_{\mathit{syn}}$.

This distinction defines both the oracle and a diagnostic failure mode. A model exhibits syntactic-call bias when it treats a call in $G_{\mathit{syn}} \setminus G_{\mathit{exec}}$ as executable. The benchmark can identify this behavior because both graphs are generated and stored as metadata.

\subsection{Dataset Generation Pipeline}

The generation pipeline proceeds through six stages: abstract tree-shaped call graph, Java class materialization, reachability query sampling, prompt construction, model output, and oracle evaluation. The generator first builds an ordered tree-shaped call graph and assigns unique Java method names. It then materializes the graph as a single Java class, samples source--target queries from the realized structure, constructs prompts containing the source program and query, and evaluates parsed model outputs against the oracle. Method declaration order is shuffled in the emitted Java class and should not encode the oracle traversal; the canonical trace is determined by executable call order inside method bodies.

\subsection{Tree-Shaped Graph Generation}

\benchmark uses acyclic, tree-shaped call graphs generated from a randomized pseudo-binary rule. Nodes correspond to Java methods, and directed edges correspond to generated method calls. The tree is ordered: when a method body is emitted, child order determines the order of call statements.

Tree construction proceeds breadth-first over nodes selected for expansion. Let $u$ be the node currently processed, and let $L(u)$ and $R(u)$ denote its left and right children. When enough method names remain, the generator creates both children:
\[
    u \rightarrow L(u), \qquad u \rightarrow R(u).
\]
The left child may then receive up to two additional children. Two independent Bernoulli variables control this local expansion:
\[
    X_{LL}(u) \sim \mathrm{Bernoulli}(p),
    \qquad
    X_{LR}(u) \sim \mathrm{Bernoulli}(p).
\]
If $X_{LL}(u)=1$, the generator creates $L(u) \rightarrow L(L(u))$; if $X_{LR}(u)=1$, it creates $L(u) \rightarrow R(L(u))$. \figref{fig:local-tree-rule} summarizes the local rule.

For each expanded node, $L(u)$ receives zero, one, or two optional children with probabilities $(1-p)^2$, $2p(1-p)$, and $p^2$. Larger values of $p$ create more branching and more sibling subtrees, which are useful for negative queries where the target appears in the class but is unreachable from the queried source. Because the method-name budget is finite, final levels may be truncated; labels and traces are computed from the realized tree rather than from an idealized full tree. We fix $p = 0.65$ to obtain sufficient branching for both positive and negative queries; sensitivity to this parameter is left to future work.

\subsection{Java Materialization and Condition-Aware Guards}

After graph construction, each node becomes one Java method. For each edge $u \rightarrow v$, the body of method $u$ contains a call to method $v$ in the child order defined by the abstract tree. In unguarded instances, these calls are emitted as executable statements. In condition-aware instances, selected calls may be emitted inside generated \texttt{if} statements. The generator assigns values to the variables used by those guards, evaluates each guard, and includes the guarded call in $G_{\mathit{exec}}$ only when the condition is true.

Other source-code features are treated as controlled surface factors unless they affect guard evaluation. Comments, local variables, method parameters, loops, and declaration order can change the text seen by the model, but they do not change reachability unless they participate in the generated guard values that decide whether a call executes. The final task definition does not use loops to guard generated reachability calls.

\subsection{Canonical Trace}

The canonical trace is the deterministic prefix of the call sequence induced by executing method calls in source order over $G_{\mathit{exec}}$. For positive queries, it stops at the first occurrence of the target. For negative queries, it contains the complete source-reachable execution region. In condition-aware instances, this convention follows executable calls only, not the larger syntactic graph.

The canonical trace is not necessarily the shortest path. A positive trace can include earlier calls that execute before the target is reached, and a negative trace can include all methods reached from the source even when the queried target is elsewhere in the class. This stricter convention separates semantic reachability from adherence to executable order: a shortest executable path may prove that the target is reachable, but it need not satisfy the benchmark's trace contract.

\subsection{Signed Canonical Trace Length}

\benchmark records a signed canonical trace length for each query. Let $\tau = \langle m_0,\ldots,m_k\rangle$ be the canonical trace, with $m_0=s$. For positive queries, the recorded value is $+k$, where $m_k=t$ is the first occurrence of the target. For negative queries, the recorded value is $-k$, where $k$ is the number of canonical execution steps needed to exhaust the source-reachable region. The sign records query polarity, and the magnitude records the amount of canonical exploration required under the benchmark convention. This measure is a trace-position measure, not a shortest-path graph distance.

\subsection{Dataset Configuration}

The frozen dataset contains \texttt{[N\_CLASSES]} classes and \texttt{[N\_INSTANCES]} queries across context sizes \texttt{[CONTEXT\_SIZES]}, canonical trace lengths \texttt{[DISTANCE\_RANGE]}, and balanced positive and negative labels at retained depths. The planned sweep uses tree-shaped graphs only and keeps the unguarded and condition-aware families under the same output schema. The metadata records class size, signed canonical trace length, query polarity, task family, syntactic graph properties, executable graph properties, and guard information.

\subsection{Oracle Validation}

Oracle validation is central to the benchmark's rigor. The validator checks that generated Java source compiles, that materialized method calls are consistent with the intended tree-shaped graph, and that sampled labels agree with reachability in $G_{\mathit{exec}}$. It also checks canonical traces, condition evaluation for guarded calls, and agreement between syntactic and executable graph metadata. These checks ensure that model errors are evaluated against the realized program rather than against an unchecked generator intention.
