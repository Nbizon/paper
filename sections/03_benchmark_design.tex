\label{sec:benchmark-design}

\subsection{Task Definition}

Each \benchmark instance contains a Java program and one reachability question. We represent an instance with the tuple
\[
    (P, s, t, f, y, \tau, m),
\]
In this tuple, $P$ is the generated program, $s$ is the source method, $t$ is the target method, and $f$ identifies the task family. The oracle provides the label $y$ and the canonical trace $\tau$. Finally, $m$ contains the controlled factors and the properties of the generated graph. The label is \true{} when execution starting from $s$ can reach $t$ through direct or indirect executable calls. Otherwise, the label is \false{}.

The prompt requires a JSON object with two fields:
\begin{itemize}[leftmargin=*]
    \item \texttt{final\_answer}: a Boolean reachability prediction;
    \item \texttt{trace}: an ordered list of method names interpreted under the benchmark's canonical trace convention.
\end{itemize}
The two fields are evaluated separately. A model can therefore return the correct final answer even when its trace is incomplete or invalid. The trace metrics are then used to identify this difference.

\subsection{Syntactic and Executable Call Graphs}

Each generated program is associated with two call graphs. The syntactic graph $G_{\mathit{syn}}$ contains all calls that are visible in the source code. The executable graph $G_{\mathit{exec}}$ contains only the calls that are executed according to the generated values and guard outcomes. For unguarded tasks, these two graphs are identical. For condition-aware tasks, a false condition can remove a visible call from $G_{\mathit{exec}}$. The executable graph is therefore a subgraph of the syntactic graph.

This distinction is used both to construct the oracle and to analyze errors. We define \emph{syntactic-call bias} as the case where a model follows an edge that belongs to $G_{\mathit{syn}}$ but not to $G_{\mathit{exec}}$. Since \benchmark stores both graphs, this behavior can be detected automatically.

\subsection{Dataset Generation Pipeline}

Figure~\ref{fig:pipeline} presents the benchmark pipeline. We first generate an ordered tree-shaped call graph, where each node receives a unique Java method name. This graph is then converted into a single Java class, and source--target questions are sampled from the generated methods. Each prompt contains the complete Java code and one reachability question. After inference, the parser extracts the final answer and the trace from the model output. The evaluator then compares these elements with the oracle. Method declarations are shuffled in the generated class so that their order in the file does not reveal the traversal. The canonical trace depends only on the order of executable calls inside method bodies.

\subsection{Tree-Shaped Graph Generation}

The generated call graph is an ordered acyclic tree. Each node is converted into a Java method, and each directed edge is converted into a method call. Because the tree is ordered, the order of the children also defines the order of calls inside the corresponding method.

The tree is generated with a breadth-first procedure. Let $u$ be the node currently expanded, and let $L(u)$ and $R(u)$ be its left and right children. When the remaining method budget is sufficient, the generator creates both children:
\[
    u \rightarrow L(u), \qquad u \rightarrow R(u).
\]
The generator can then add two children below $L(u)$. These two additions are sampled independently:
\[
    X_{LL}(u) \sim \mathrm{Bernoulli}(p),
    \qquad
    X_{LR}(u) \sim \mathrm{Bernoulli}(p).
\]
When $X_{LL}(u)=1$, the edge $L(u) \rightarrow L(L(u))$ is added. Similarly, when $X_{LR}(u)=1$, the edge $L(u) \rightarrow R(L(u))$ is added. Figure~\ref{fig:local-tree-rule} illustrates this local rule.

With this rule, $L(u)$ receives zero, one, or two optional children with probabilities $(1-p)^2$, $2p(1-p)$, and $p^2$, respectively. A larger value of $p$ produces more branches. It therefore creates more situations where the target exists in the class but cannot be reached from the selected source. The method budget can truncate the last level of the tree. Oracle labels and traces are always computed from the final generated tree, after this truncation. We use $p=0.65$ to produce enough branching for positive and negative questions. A study of the sensitivity to this value is left for future work.

\subsection{Java Materialization and Condition-Aware Guards}

Once the tree has been generated, each node is translated into one Java method. For each edge $u \rightarrow v$, a call to $v$ is inserted into the body of $u$. Calls follow the child order defined by the tree. In unguarded instances, calls are inserted directly into the method body. In condition-aware instances, some calls are placed inside generated \texttt{if} statements. The generator also fixes the values used by these conditions and evaluates each guard. A guarded call is included in $G_{\mathit{exec}}$ only when its condition is true.

The generator can also vary comments, local variables, parameters, loops, and the order of method declarations. These elements are considered surface factors unless they are used to compute a condition. They can make the code longer or change its appearance, but they do not otherwise change reachability. In the current task definition, reachability calls are not placed inside loops.

\subsection{Canonical Trace}

For each question, the oracle constructs one canonical trace by following executable calls in source order. For a positive question, the traversal stops when the target is reached for the first time. For a negative question, it continues until all methods reachable from the source have been explored. In condition-aware instances, the traversal follows $G_{\mathit{exec}}$ and ignores calls whose conditions are false.

The canonical trace is not necessarily the shortest path between the source and the target. Before reaching a positive target, execution can first explore a sibling subtree that appears earlier in the method body. For a negative question, the trace contains all methods reachable from the source, even if the target is located in another part of the class. As a result, a shortest path can be sufficient to justify a \true{} answer but still be different from the canonical trace expected by the benchmark.

\subsection{Signed Canonical Trace Length}

We use a signed canonical trace length to represent the amount of exploration required by a question. Let $\tau = \langle m_0,\ldots,m_k\rangle$, with $m_0=s$. For a positive question, the length is $+k$ and $m_k=t$ corresponds to the first occurrence of the target. For a negative question, the length is $-k$, where $k$ is the number of steps needed to explore the complete region reachable from the source. The sign therefore represents the query polarity, while the magnitude represents the length of the required exploration. This value is not a shortest-path distance.

\subsection{Dataset Configuration}

The final dataset contains \texttt{[N\_INSTANCES]} questions with context sizes \texttt{[CONTEXT\_SIZES]} and canonical trace lengths \texttt{[DISTANCE\_RANGE]}. Positive and negative labels are balanced for the retained trace lengths. Both task families use tree-shaped graphs and the same response format. For each question, the metadata contains the class size, signed trace length, polarity, task family, properties of the syntactic and executable graphs, and information about generated conditions.

\subsection{Oracle Validation}

The last step validates the oracle against the generated source code. The validator compiles each Java class, compares the generated calls with the intended tree, and recomputes reachability in $G_{\mathit{exec}}$. It also checks the canonical trace, the result of each generated condition, and the executable-graph metadata. The expected answers therefore come from the final generated program and not only from the internal state of the generator.
