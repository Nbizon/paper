\section{Benchmark Design}
\label{sec:benchmark-design}

\begin{itemize}[leftmargin=*]
    \item Goal: define a controlled benchmark artifact for evaluating structural reasoning in LLMs on Java reachability tasks.

\end{itemize}

\subsection{Task Definition}

Each benchmark instance presents the model with a generated Java class and a natural-language reachability question of the form: does method A call method B directly or indirectly? The model must answer this base task for both control-flow and data-flow instances. In both families, the generated code is compilable, the variable management is correct, and the generated program is consistent with the oracle.

\indent \textbf{Common input:}
\begin{itemize}[leftmargin=*]
    \item a generated Java class;
    \item a natural-language question of the form: does method A call method B directly or indirectly?
\end{itemize}

\textbf{Control-flow versus data-flow distinction:}
\begin{itemize}[leftmargin=*]
    \item in control-flow instances, method calls are placed outside control-flow structures;
    \item in data-flow instances, method calls may appear inside control-flow structures such as \texttt{if} statements, so the model must evaluate the relevant condition to decide whether the call is executed;
    \item apart from this placement of method calls inside or outside control-flow structures, the task remains the same reachability question over compilable Java code with correct generated variables.
\end{itemize}

\textbf{Output schema:}
\begin{itemize}[leftmargin=*]
    \item \texttt{trace};
    \item \texttt{final\_answer}.
\end{itemize}

\textbf{Oracle design:}
\begin{itemize}[leftmargin=*]
    \item positive control-flow case: the DFS call path from source to target; method calls remain outside control-flow constructs such as \texttt{if}, \texttt{while}, and \texttt{for};
    \item negative control-flow case: the DFS traversal path from the source used to visit all nodes in the subtree; method calls remain outside control-flow constructs such as \texttt{if}, \texttt{while}, and \texttt{for};
    \item positive data-flow case: the DFS call path from source to target; method calls may appear inside control-flow constructs such as \texttt{if}, \texttt{while}, and \texttt{for};
    \item negative data-flow case: the DFS traversal path from the source used to visit all nodes in the subtree; method calls may appear inside control-flow constructs such as \texttt{if}, \texttt{while}, and \texttt{for};
\end{itemize}

\subsection{Dataset Generation Pipeline}

\begin{itemize}[leftmargin=*]
    \item Step 1: sample method names and build an abstract graph structure.
    \item Step 2: materialize the graph as Java code with optional distractors.
    \item Step 3: sample questions and write the oracle files.
\end{itemize}

The pipeline is ultimately meant to support two complementary task families:
\begin{itemize}[leftmargin=*]
    \item \textbf{Control-flow reachability}: a reachability task of the form ``does method A call method B directly or indirectly?'' without taking variable values or control flow into account. Method calls are placed outside control structures, and variables do not have a concrete influence on control flow.
    \item \textbf{Data-flow reachability}: the same reachability task over generated, compilable Java code, but method calls may appear inside control structures. Variables and parameters are generated correctly and may determine whether a guarded call is executed.
\end{itemize}

The implementation makes the following design choices:
\begin{itemize}[leftmargin=*]
    \item The benchmark language is Java.
    \item Method names are sampled from plausible verb/noun fragments in camelCase.
    \item Method bodies are shuffled within the class to prevent solutions based only on position.
    \item Positive and negative questions are sampled at each depth, so reachable and unreachable decisions can be studied separately.
    \item Stored artifacts for each case include the generated class, prompt, reachability questions, oracle chains, method list, and configuration metadata.
\end{itemize}

\subsection{Generated Call-Graph Structures}

Each generated Java class is the textual representation of an underlying directed call graph. Nodes correspond to methods, and directed edges correspond to method calls. Reachability questions are asked over this graph, not over the textual order of methods in the file. That distinction matters because method bodies are shuffled before the class is written: a method can appear late in the file while sitting close to the root of the call graph, or the reverse. Solving the task therefore requires reconstructing call relations from code rather than relying on textual position.

\subsubsection{Linear Structure}

In the linear configuration, the generator builds one or more method chains. Within a chain, method $m_i$ calls only its successor $m_{i+1}$, and the final method has no outgoing call. The graph is therefore a directed path. Position in the chain determines reachability: a query $(m_i, m_j)$ is positive when $i < j$, because execution can follow successor edges from $m_i$ to $m_j$. A query is negative when the target is upstream or outside the suffix reachable from the source. For example, $m_2$ reaches $m_5$, but $m_4$ does not reach $m_2$ because calls never go backward. Linear graphs isolate path-following behavior by varying depth without adding branching.

\subsubsection{Tree Structure}

In the tree configuration, the generator builds a rooted directed tree. Each method can call its children, and leaves have no outgoing call. A target is reachable from a source exactly when it lies in the source's descendant subtree. In Figure~\ref{fig:generated-call-graphs}(b), $u_0$ reaches every node in the fragment, while $R(u_0)$ does not reach $R(L(u_0))$ because that target belongs to a sibling subtree.

Tree instances introduce two difficulties absent from linear chains. First, a model must follow multiple outgoing calls from the same method. Second, negative examples require branch-sensitive reasoning: the target method may appear in the same Java class, even close by in the textual file, while remaining unreachable from the queried source. For that reason, tree cases better resemble common comprehension tasks such as impact analysis, security reachability checks, and debugging through call hierarchies.

Tree generation uses breadth-first construction with a probabilistic local expansion rule. For each processed node $u$, the generator creates deterministic left and right children when enough method names remain. It may then expand the left child one level further with two independently sampled descendants. Figure~\ref{fig:local-tree-rule} illustrates this local rule: the skeleton edges are always present, while the optional descendants under $L(u)$ are controlled by Bernoulli draws with parameter $p$.

When $p=0$, the generator keeps the deterministic left and right children but never expands the left child further, producing a right-spine tendency with left leaves. When $p=1$, every generated left child is expanded immediately, yielding denser branching and more sibling subtrees. Figure~\ref{fig:p-extremes} makes these extremes concrete.

For a finite context size $N$, the process stops when the generated method-name list is exhausted. The probability rule therefore governs local growth before exhaustion, while the final levels may still be truncated when too few method names remain. For that reason, \benchmark stores the realized tree and derives questions from that graph rather than from the probability model alone.

\subsubsection{From Graph to Java Code}

After constructing the abstract graph, the generator emits one Java method per node. For an edge $u \rightarrow v$, the body of method $u$ contains a call to method $v$. Depending on the configuration, method bodies may also contain comments, local variables, loops, conditionals, and parameters. These elements vary the surface complexity of the code while preserving the underlying reachability relation. The final method order in \texttt{TheClass.java} is randomized, so the benchmark measures call-graph reconstruction rather than reading order. In the data-flow family, the same skeleton allows method calls to appear inside control structures whose conditions are determined by correctly generated variables and parameters.

\subsection{Prompting Protocol}

\begin{itemize}[leftmargin=*]
    \item The same task framing is used for all models within a task family.
    \item The prompt must define the JSON output schema and the expected trace format.
    \item Invalid JSON and malformed traces are handled explicitly by the evaluator.
\end{itemize}

\subsection{Benchmark Outputs and Metadata}

Each generated case is stored in a small directory whose files are sufficient to reproduce the prompt and the oracle:
\begin{itemize}[leftmargin=*]
    \item \texttt{TheClass.java}: generated source program.
    \item \texttt{system.txt}: task instructions plus source code.
    \item \texttt{reachability\_questions.txt}: one question per line, prefixed by a signed distance.
    \item \texttt{chains.txt}: expected trace/chain aligned with the question index.
    \item \texttt{methods.txt}: generated method names.
    \item \texttt{config.json}: context size, depth range, comments, variables, loops, conditionals, and parameters.
\end{itemize}
