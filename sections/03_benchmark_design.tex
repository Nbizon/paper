\subsection{Task Definition}

\benchmark evaluates one question under a fixed output contract. Each instance gives the model a generated Java class, a source method, and a target method, then asks whether execution starting at the source can reach the target through direct or indirect method calls. The oracle label is this Boolean reachability relation: \true{} if the target is reachable in the executable call graph, and \false{} otherwise. The required output is a JSON object with a Boolean \texttt{final\_answer} and a \texttt{trace}, an ordered list of method names interpreted under the benchmark's traversal convention.

The same schema is used for two task families. In unguarded reachability, generated calls are not placed behind \texttt{if}, \texttt{for}, or \texttt{while} guards, so every generated call is executable. In condition-aware reachability, a call may remain unguarded or may appear inside a generated \texttt{if} statement; a false condition leaves the call visible in the source but removes it from the executable call graph. Loops are not used to guard calls in the final task definition.

\subsection{Dataset Generation Pipeline}

The dataset starts from tree-shaped call graphs. The pipeline samples unique Java method names, builds an ordered abstract call tree, materializes it as a single Java class, and samples positive and negative questions from the realized structure. The resulting artifacts include the Java source, prompt context, questions, oracle traces, and configuration metadata.

This design keeps the oracle simple enough to validate while varying properties that matter for LLM evaluation. Context size, source-target distance, label polarity, comments, local variables, parameters, loops, and conditionals are controlled by configuration. Label polarity refers only to whether the target is reachable from the source, not to trace correctness. Method declarations are shuffled in the emitted class, so declaration order is not a shortcut for the oracle traversal.

\subsection{Syntactic and Executable Call Graphs}

Condition-aware instances have two relevant call graphs. The \emph{syntactic call graph} contains all method calls visible in the Java source, including calls inside branches that do not execute. The \emph{executable call graph} keeps only calls that run under the generated values and conditions. A guarded call can therefore be present in the source program while absent from the oracle graph.

This distinction is part of the benchmark semantics, not a post-hoc error category. Later, \secref{sec:error-analysis} uses \emph{syntactic-call bias} for the model failure mode in which a visible call is treated as executable even though it appears only in a non-executed branch.

\subsection{Tree-Shaped Graph Generation}

The benchmark uses acyclic, tree-shaped call graphs generated from randomized pseudo-binary trees. Nodes correspond to Java methods, and directed edges correspond to generated method calls. The tree is ordered: when a method body is materialized, child order determines the order of call statements. This makes the canonical trace code-aligned while declaration order remains uninformative.

Tree construction proceeds breadth-first over nodes selected for expansion. Let $u$ be the node currently processed, and let $L(u)$ and $R(u)$ denote its left and right children. When enough method names remain, the generator creates both children:
\[
    u \rightarrow L(u), \qquad u \rightarrow R(u).
\]
The left child may then receive up to two additional children. Two independent Bernoulli variables control this local expansion:
\[
    X_{LL}(u) \sim \mathrm{Bernoulli}(p),
    \qquad
    X_{LR}(u) \sim \mathrm{Bernoulli}(p).
\]
If $X_{LL}(u)=1$, the generator creates $L(u) \rightarrow L(L(u))$; if $X_{LR}(u)=1$, it creates $L(u) \rightarrow R(L(u))$. \figref{fig:local-tree-rule} summarizes the local rule.

The role of $p$ is intentionally local and easy to interpret. For each expanded node, $L(u)$ receives zero, one, or two optional children with probabilities $(1-p)^2$, $2p(1-p)$, and $p^2$, respectively. Larger values create more branching and more sibling subtrees, which are useful for negative queries where the target is present in the class but unreachable from the queried source. Because the method-name budget is finite, the final levels may be truncated; labels and traces are always computed from the realized tree, not from an idealized full tree.

We fix the tree-expansion parameter to $p = 0.65$, based on a preliminary calibration of how $p$ affects the number of usable questions per generated class, especially at deeper canonical distances. \subsection{From Graph to Java Code}

After constructing the abstract tree, the generator emits one Java method per node. For each edge $u \rightarrow v$, the body of method $u$ contains a call to method $v$. In unguarded instances, these calls are executable by construction. In condition-aware instances, selected calls are placed inside generated \texttt{if} statements whose truth values determine whether they belong to the executable graph. Other code-surface elements vary the amount and shape of source code around the calls, but they are not intended to change reachability.

\subsection{Canonical Execution-Oriented Trace}

The oracle trace is defined over the executable graph and aligned with the generated code. Because child order is materialized as the order of call statements, the oracle explores calls as they appear inside each method body.

For positive queries, the trace is the first execution-consistent exploration that reaches the target. It is not necessarily the shortest path. For negative queries, the trace exhausts the region reachable from the source without finding the target. In condition-aware instances, this traversal follows the executable call graph, not the larger syntactic graph.

\subsection{Signed Canonical Distance}

The benchmark records a signed canonical distance for each query. Positive queries use $+d$, where $d$ is the target position in the canonical trace. Negative queries use $-d$, where $d$ is the size of the explored source-reachable region minus one. The sign mirrors the Boolean label, while the magnitude gives a trace-based difficulty proxy.

The planned sweep uses tree-shaped graphs only. It varies context sizes 100, 250, and 500 and targets absolute canonical distances from 1 to 25. \subsection{Oracle Validation}

Generated instances are checked by a programmatic oracle-validation pipeline. The validator checks that the Java source compiles, that materialized method calls match the intended tree-shaped graph, and that sampled positive and negative queries agree with the reachability relation induced by the generated program. It also checks that oracle traces follow the canonical execution-oriented traversal. For condition-aware instances, validation additionally checks that generated variables and conditions correctly determine whether guarded calls execute.
