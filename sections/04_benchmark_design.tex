\section{\benchmark Design}
\label{sec:benchmark-design}

\benchmark is the final dataset produced by a configurable construction algorithm. This algorithm controls the method structure, the values that determine which calls execute, and the presentation of the code. Figure~\ref{fig:pipeline} shows the construction of this dataset and the evaluation of model responses. The labels and executable graphs belong to the generated dataset and are checked independently on all its classes and questions in Section~\ref{subsec:oracle-validation}.

\subsection{Task Instances and Execution Context}

Each instance contains a Java class named \texttt{TheClass}, a source method $s$, and a target method $t$. This class contains all generated methods, including those outside the region reachable from $s$. A root method with no parameters defines the entry point of the program. Its local declarations initialize values that can then be passed to other methods.

We represent an instance as
\[
    (P, e, s, t, f, y, G_{\mathit{exec}}, m),
\]
where $P$ is the class, $e$ is the execution context starting from the root, and $f$ identifies the task family. The label $y$ is \true{} when $t$ can execute from $s$ with the argument values supplied by $e$, and \false{} otherwise. The graph $G_{\mathit{exec}}$ records executable calls, while $m$ stores the generation settings and question metadata. The source named in the question is not necessarily the root. A separate \texttt{Main} class can make this context explicit by invoking the root, but the launcher method is not included in the oracle graph.

\subsection{Constructing the Method Structure}

The algorithm first generates unique method names by combining a verb, a noun, and a suffix. This provides identifiers resembling Java method names, without specifying what the generated bodies do. Each name becomes a node in a single acyclic tree whose size corresponds to the configured number of methods.

The tree is expanded using a queue. For a node $u$ taken from this queue, the algorithm creates a left child $L(u)$ and a right child $R(u)$, as long as method names remain available. Additional branches can then be created below $L(u)$. Its two possible children are sampled independently, each with probability $p=0.65$:
\[
    X_{LL}(u),X_{LR}(u)\sim\mathrm{Bernoulli}(p).
\]
The right child and any sampled grandchildren are added to the queue for further expansion. Figure~\ref{fig:local-tree-rule} illustrates this rule. When no method names remain, no further nodes are created. This construction provides reachable regions of different sizes and methods outside these regions that can be used as negative targets.

\subsection{Generating Methods and Propagating Values}

Once the tree is available, each node is translated into a public instance method returning \texttt{void}. The root has no parameters, while the other methods receive the configured number of parameters. Their types are selected from \texttt{int}, \texttt{long}, \texttt{boolean}, \texttt{float}, and \texttt{double}. When a parent method has parameters, its children's parameter types are selected from those already present in the parent. This allows values to be passed through successive calls.

For each edge in the tree, the caller supplies arguments with the types required by the callee. The algorithm can reuse a compatible parameter or an argument variable already introduced, or create a local variable when needed. It records the concrete value supplied to each callee parameter before generating its body. The root must therefore initialize values for its parameterized children, while later methods can also introduce new values. As a consequence, a condition may depend on a value declared several methods earlier.

The configured number of local variables controls additional synthetic declarations. Variables needed to supply call arguments are counted separately. This means that a configuration with no additional local variables can still contain declarations needed to initialize execution, as illustrated in Figure~\ref{fig:background-example}.

\subsection{Conditions and Presentation Factors}

The number of generated condition blocks per method, denoted by \texttt{nb\_if}, defines the study's two task families. When \texttt{nb\_if}$=0$, calls corresponding to tree edges are unguarded. When \texttt{nb\_if}$>0$, these calls can appear directly in the body or inside a generated \texttt{if} block. For a call placed inside a condition, the algorithm constructs this condition so that it evaluates to true with the recorded argument values.

A condition block that has not been used can instead contain calls to existing methods behind a false guard. The selected methods must accept arguments available in the caller and must differ from the caller and its direct executable callees. These calls remain visible in the code but are excluded from the executable graph. They can connect separate branches or point back to an ancestor, while remaining disabled during the rooted execution. Conditions use Boolean equality or inequality, or numeric comparisons with thresholds chosen to obtain the required result. When no suitable value is available, literal \texttt{true} or \texttt{false} conditions are used. Although generation is randomized, the resulting program has a fixed execution.

Comments, additional local variables, and loops allow the presentation of the code to vary. Comments contain generated Lorem Ipsum text. Loop blocks use \texttt{for} or \texttt{while}, with one to five iterations, and contain printing rather than calls to benchmark methods. These blocks therefore add code without guarding the calls that determine reachability. Condition and loop blocks are shuffled inside methods, and method declarations are shuffled inside the class. As a consequence, their position in the class does not reveal the call order.

The maintained generator also allows calls corresponding to tree edges to remain outside guards when condition blocks are present. The evaluated archive uses the condition-aware construction with \texttt{nb\_if}$\in\{0,1,3,5\}$. The study groups are defined by this count rather than by the mode name stored in the archive.

\subsection{Constructing the Oracle and Selecting Questions}

While generating each Java body, the algorithm records its executable callees in the order in which the calls are emitted. Unguarded calls and calls behind true guards are included, while calls behind false guards are excluded. These lists define $G_{\mathit{exec}}=(V,E_{\mathit{exec}})$. Recording this order is needed because shuffling code blocks can change the exploration order even when reachability remains the same.

The algorithm then explores this graph from candidate source methods. For a positive question, it selects a target encountered during a source-first depth-first exploration. For a negative question, it selects an existing method outside the complete region $R_e(s)$ reachable from the source. Both types of questions therefore refer to methods declared in the class, rather than using invented names for negative targets.

The signed generation distance $d$ describes this reference exploration. For a positive question, $d$ is the target's position after the source, whose position is zero. For a negative question, $d=-(|R_e(s)|-1)$. This distance is therefore not generally the length of the shortest path. A positive trace may reach the target without visiting branches encountered earlier in the reference exploration, while a negative trace must cover the complete reachable region.

Questions are sampled to obtain the configured number for each polarity and distance. When one class does not provide enough candidates, additional classes are generated to complete these quotas. The Java code is retained together with the executable graph, method inventory, questions, and generation configuration. The maintained format stores the graph directly, while the evaluated archives retain executable trees from which the same relationships are recovered. The historical chain files do not require the model to follow one particular exploration order.

\subsection{Prompting Variants of \benchmark}
\label{subsec:prompt-design}

The system message explains executable reachability, specifies the JSON response, and presents the complete class containing its different methods. A separate user message names the source and target and asks whether the former calls the latter directly or indirectly. The response contains two fields: \texttt{final\_answer}, with the value \texttt{"True"} or \texttt{"False"}, and \texttt{trace}, listing the explored methods. Although the archived prompt asks for execution order, the evaluator accepts any exploration satisfying the rules in Section~\ref{subsec:scoring}.

We consider two variants of the final benchmark: \benchmark~(CO), for \emph{Class-only}, and \benchmark~(EE), for \emph{Explicit execution}. Both use the same \texttt{TheClass} programs, source--target questions, Boolean labels, executable-graph oracles, and scoring rules. They differ in the execution information made explicit in the prompt. The archives identify these prompt variants as v1 and v4.

In \benchmark~(CO), the code block contains only \texttt{TheClass}. The prompt does not explicitly identify the entry point or state that all values and execution outcomes needed to answer the question are determined by the code. When the source has parameters, the model must infer the intended execution from the root and recover the values supplied to this source from the class. Without this information being explicit, a parameter may be treated as an unspecified input, even though its value is fixed by the generated execution. This adds an interpretation step, particularly when the arguments determine whether guarded calls execute.

In \benchmark~(EE), the code block also contains a separate \texttt{Main} launcher, which creates an instance of \texttt{TheClass} and calls its root without arguments. The prompt states that the supplied code describes a concrete execution, that all relevant values and outcomes can be determined statically, and that no external inputs should be assumed. The model is asked to follow values from the entry point and use them to evaluate conditions, branches, and loops.

EE therefore makes explicit the execution context already used by the common oracle, while CO also requires the model to infer it. The classes have the same structural complexity in both variants. The returned trace starts at the queried source and uses the same response fields. \researchq{3} compares performance and token use between these two presentations of the same dataset.
