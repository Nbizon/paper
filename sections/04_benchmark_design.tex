\section{\benchmark Design}
\label{sec:benchmark-design}

\benchmark is the final generated benchmark used in our evaluation. It contains 1,232 Java classes and 46,656 reachability questions, together with their Boolean labels and executable-graph oracles. The construction algorithm described in this section produces this dataset by controlling the call structure, the values that determine execution, and the presentation of each class. We use the name \benchmark for the resulting dataset and refer separately to the algorithm that constructs it. Figure~\ref{fig:pipeline} summarizes construction and evaluation.

\subsection{Task Instances and Execution Context}

Each instance contains a Java class \texttt{TheClass}, a source method $s$, and a target method $t$. The class contains all generated methods, including methods outside the region reachable from $s$. One parameter-free root defines the program entry point. Its local declarations initialize the values subsequently passed between methods.

We represent an instance as
\[
    (P, e, s, t, f, y, G_{\mathit{exec}}, m),
\]
where $P$ is the class, $e$ is its rooted execution context, and $f$ identifies the task family. The label $y$ is \true{} when $t$ is executable from $s$ under the argument values supplied by $e$, and \false{} otherwise. The graph $G_{\mathit{exec}}$ records the executable calls; $m$ contains generation settings and question metadata. The queried source need not be the root. A separate \texttt{Main} class can make $e$ explicit by invoking this root, but its launcher method is not a node of the oracle.

\subsection{Constructing the Method Structure}

The algorithm first generates unique method names by combining a verb, a noun, and a suffix. These names provide Java-like identifiers without specifying the behavior of the generated method bodies. Each name becomes a node in a single acyclic tree whose size is the configured number of methods.

A queue controls the expansion. For an expanded node $u$, the algorithm creates left and right children, $L(u)$ and $R(u)$, while names remain available. It then independently attempts to add the two children of $L(u)$, each with probability $p=0.65$:
\[
    X_{LL}(u),X_{LR}(u)\sim\mathrm{Bernoulli}(p).
\]
The right child and any sampled grandchildren enter the queue for subsequent expansion. Figure~\ref{fig:local-tree-rule} shows this local rule. Expansion consumes the method budget, so the final additions are truncated when no names remain. The resulting branches provide source regions of different sizes and methods outside those regions for negative queries.

\subsection{Generating Methods and Propagating Values}

Each node is translated into a public instance method returning \texttt{void}. The root has no parameters; other methods receive the configured number of parameters. Their types are drawn from \texttt{int}, \texttt{long}, \texttt{boolean}, \texttt{float}, and \texttt{double}. Below a parameterized parent, parameter types are sampled from those already present in the parent, allowing values to propagate through successive calls.

For each structural edge, the caller supplies arguments of the required types. The algorithm reuses compatible parameters or previously introduced argument variables, or creates a local variable when needed. It records the concrete value assigned to each callee parameter before generating that method's body. The root necessarily introduces local values for its parameterized children; later methods may introduce fresh values as well. A condition can therefore depend on a local origin several method boundaries away, rather than only on a declaration in its own method.

The configured local-variable count controls additional synthetic declarations. Variables introduced to supply call arguments are separate from this count. Consequently, a configuration with no additional local variables can still contain the declarations needed to initialize execution, as in Figure~\ref{fig:background-example}.

\subsection{Conditions and Presentation Factors}

The number of generated condition blocks per method, denoted by \texttt{nb\_if}, defines the study's two task families. When \texttt{nb\_if}$=0$, edge-defining calls are unguarded. When \texttt{nb\_if}$>0$, these calls can be placed either directly in the body or inside generated \texttt{if} blocks. Calls assigned to a guarded block receive a condition constructed to evaluate to true under their recorded argument values.

An otherwise unused condition block can instead contain calls to existing methods behind a false guard. Candidates exclude the caller and its direct executable callees, and must accept arguments available in the caller. These visible calls do not enter the executable graph. They can connect separate branches or point back to an ancestor, while remaining disabled under the rooted execution. Conditions use Boolean equality or inequality, or numeric comparisons against thresholds chosen to produce the intended outcome. Without a suitable tested value, literal \texttt{true} or \texttt{false} conditions are used. Generation is randomized, but the resulting program defines a fixed execution.

Comments, additional local variables, and loops vary the presentation. Comments contain generated Lorem Ipsum text. Loop blocks use \texttt{for} or \texttt{while}, with one to five iterations, and contain printing rather than calls to benchmark methods. They therefore add code without guarding the calls that determine reachability. Condition and loop blocks are shuffled within methods, and method declarations are shuffled within the class. Declaration order consequently does not reveal call order.

The maintained generator also supports keeping edge-defining calls outside guards when condition blocks are present. The evaluated archive uses the condition-aware construction with \texttt{nb\_if}$\in\{0,1,3,5\}$; its study groups are defined by this count rather than the archived mode name.

\subsection{Constructing the Oracle and Selecting Questions}

While emitting each Java body, the algorithm records its executable callees in their emitted order. Unguarded calls and calls protected by true guards are recorded; calls under false guards are excluded. These lists define $G_{\mathit{exec}}=(V,E_{\mathit{exec}})$. This step is needed because shuffling blocks can change exploration order even when the tree's reachability relationships remain the same.

The algorithm then explores this graph from candidate source methods. Positive questions select a target encountered in a source-first depth-first exploration. Negative questions select an existing method outside the complete source-reachable region $R_e(s)$. Both polarities therefore refer to methods declared in the class; a negative target is not an invented method name.

The signed generation distance $d$ describes this reference exploration. For a positive query, $d$ is the target's position after the source, whose position is zero. For a negative query, $d=-(|R_e(s)|-1)$. Its magnitude is therefore not generally a shortest-path length. A positive trace may reach the target without visiting branches encountered earlier in the reference exploration, whereas a negative trace must cover the entire region.

Questions are sampled to meet the configured quota for each polarity and distance. When one class does not provide enough candidates, further classes are generated to complete these quotas. The executable graph, method inventory, questions, and generation configuration are retained with the Java code. The maintained format stores the graph directly; the evaluated archives retain executable-tree files from which the same relationships are recovered. Historical chain files do not prescribe the model's exploration order.

\subsection{Prompting Variants of \benchmark}
\label{subsec:prompt-design}

The system message defines executable reachability, specifies the JSON response, and presents the complete class containing its different methods. A separate user message names the source and target and asks whether the former calls the latter directly or indirectly. The response has two fields: \texttt{final\_answer}, with the value \texttt{"True"} or \texttt{"False"}, and \texttt{trace}, listing explored methods. The archived wording asks for execution order, while scoring accepts any exploration satisfying the rules in Section~\ref{subsec:scoring}.

We distinguish two variants of the final benchmark: \benchmark~(CO), for \emph{Class-only}, and \benchmark~(EE), for \emph{Explicit execution}. Both use the same \texttt{TheClass} programs, source--target questions, Boolean labels, executable-graph oracles, and scoring rules. Their difference concerns the execution information made explicit in the prompt. The archives identify these prompt variants as v1 and v4.

In \benchmark~(CO), the code block contains only \texttt{TheClass}. The prompt does not explicitly identify the program entry point or state that all values and execution outcomes relevant to the question are determined by the supplied code. For a parameterized source, the model must infer the intended rooted execution and recover the values supplied to that source from the class. Without this clarification, a parameter may be interpreted as an unspecified input even though the generated execution fixes its value. CO thus introduces an additional interpretation step, particularly when those arguments control guarded calls.

In \benchmark~(EE), the code block also contains the separate \texttt{Main} launcher, which instantiates \texttt{TheClass} and invokes its parameter-free root. The prompt additionally states that the code is a self-contained specification of a concrete execution, that every relevant value and outcome can be determined statically, and that no external inputs should be assumed. It asks the model to propagate values from the entry point and use them to evaluate conditions, branches, and loops.

The additional launcher and instructions in EE expose the execution context already used by the common oracle. The generated class and expected answers remain identical. EE still requires the model to follow calls, propagate values, and evaluate guards, while CO also requires it to infer the execution assumptions. This makes the CO formulation more demanding without increasing the structural complexity of the programs. In both variants, the returned trace starts at the queried source, and the response fields are the same. \researchq{3} examines the performance difference associated with these two presentations of the same benchmark.
