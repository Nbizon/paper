\section{Understanding Trace Errors}
\label{sec:error-analysis}

The metrics used in \researchq{3} indicate whether a trace is correct, complete, or graph-valid. However, two incorrect traces can fail for different reasons. One may stop too early, while another may continue through a call that cannot execute. We therefore classify the errors before inspecting individual examples.

\subsection{From a Failed Trace to an Error Type}

Each predicted trace is compared with the method list, the executable graph, and the canonical trace. This comparison produces the taxonomy shown in Table~\ref{tab:error-taxonomy}. The categories are not inferred from generated explanations. They are detected from observable differences between the predicted trace and the oracle.

\input{tables/error_taxonomy}

The order of the checks makes it possible to separate several levels of failure. We first verify that the response can be parsed and that the trace starts from the requested source. We then check whether the methods exist and whether consecutive methods are connected by executable edges. Finally, we compare the exploration order and stopping point with the canonical trace. A response can satisfy an early check and still fail a later one. For example, all reported transitions can be executable even when the model stops before reaching the target.

\subsection{When Visible Code Does Not Execute}

Condition-aware programs introduce one error that can be identified more precisely. A call can appear explicitly in the source code while its condition is false. If the model follows this call, the transition exists in $G_{\mathit{syn}}$ but not in $G_{\mathit{exec}}$. We call this behavior syntactic-call bias because the trace follows the visible syntax without reproducing the runtime condition.

Figure~\ref{fig:syntactic-call-bias} illustrates this difference. Both calls can be found by reading the method body, but only \texttt{B} is executed for the generated value. The oracle trace therefore excludes \texttt{C}. This error is different from hallucinating a method or inventing an edge, because the model follows code that really exists but does not execute.

\subsection{Using the Errors for Diagnosis}

An interactive dashboard groups the detected errors by model configuration, structural factors, reasoning budget when verified, and local graph motif. We use these groups to determine whether an error appears repeatedly under the same conditions. For example, a model may return correct Boolean answers while frequently omitting intermediate methods, or it may increasingly follow disabled calls as the number of conditions grows.

The dashboard does not define the benchmark scores. All metrics and error labels are computed by the frozen evaluator before the examples are inspected. The examples are then used to explain a measured pattern, not to establish it.
