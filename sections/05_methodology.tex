\section{Experimental Methodology}
\label{sec:methodology}

The benchmark defines how programs and questions are generated. We now describe how these questions are used to evaluate a model. The experiment follows four main steps. We first select the validated instances, then run each model with the same prompt, parse its response, and finally compare the parsed answer and trace with the oracle. All decisions are fixed before the final run. Values that depend on the final release remain between brackets until the dataset and model configurations are frozen.

\subsection{Preparing the Evaluation Set}
\label{subsec:evaluation-set}

The evaluation set contains \texttt{[N\_INSTANCES]} questions sampled from \texttt{[N\_CLASSES]} generated Java classes. It covers context sizes \texttt{[CONTEXT\_SIZES]}, signed trace lengths \texttt{[TRACE\_LENGTH\_RANGE]}, task families \texttt{[TASK\_FAMILIES]}, guard settings \texttt{[GUARD\_SETTINGS]}, code-surface settings \texttt{[PARAMETER\_SETTINGS]}, and random seeds \texttt{[RANDOM\_SEEDS]}. The resulting balance between positive and negative questions is \texttt{[POSITIVE\_NEGATIVE\_BALANCE]}.

We include a question only when the generator and validator agree on the methods contained in the compiled class, the reachability label, the canonical trace, and the executable graph. For condition-aware questions, they must also agree on the outcome of the generated conditions. Positive and negative questions are selected in pairs at each trace length when both are available. When a configuration does not contain both labels, we report its actual size and do not use it in an analysis that requires exact balance.

The main factors used in the analysis are the task family, signed trace length, class size, query polarity, and model configuration. For condition-aware programs, we also record the number of conditions and the number of calls disabled by these conditions. Comments, variables, parameters, loops, and declaration order are treated as main factors only when they are varied systematically in the final dataset. Otherwise, they remain descriptive metadata.

The unguarded and condition-aware families use similar factor distributions whenever possible. However, the current generator does not create two versions of the same abstract program automatically. Unless this functionality is added before the final run, the comparison between the two families is unpaired.

\input{tables/dataset\_specification}

Each Java class is stored with all the information needed by the experiment. This includes the source code, questions, method list, oracle graphs, canonical traces, generated conditions, and generation parameters. The inference program only reads these files. Model responses are saved separately so that parsing and scoring can be repeated without running inference again.

\subsection{Running the Models}
\label{subsec:model-configurations}

A model name alone is not sufficient to describe an experiment. The same checkpoint can produce different results depending on the serving backend, numerical precision, context limit, decoding parameters, or output budget. We therefore consider each complete deployment as one model configuration.

\input{tables/models}

Each configuration records the checkpoint and revision, backend and version, numerical precision, tensor parallelism, context limit, chat template, decoding parameters, output-token limit, stopping criteria, concurrency, and reasoning control when one is available. These values are stored in a run manifest together with the hardware, complete backend command, memory settings, and random seed when supported.

All models are served locally through an OpenAI-compatible endpoint. For each model and question, the runner sends one request and stores the raw output together with its metadata and execution status. Requests use the fixed retry policy \texttt{[RETRY\_POLICY]}. If all attempts fail, the question remains in the evaluation and is marked as \texttt{NO\_RESPONSE}. We use deterministic decoding when it is supported. When the backend cannot guarantee determinism, this limitation is recorded in the manifest.

Some backends allow the requested reasoning budget to be controlled. We analyze this factor only when the backend documents the control and the saved metadata confirms that the requested value was accepted. The result then describes this particular deployment and is not generalized to every use of the checkpoint.

\subsection{From the Prompt to a Parsed Response}
\label{subsec:prompt-calibration}
\label{subsec:parsing}

Before the final experiment, we test several prompt versions on a pilot set generated with separate random seeds. These pilot questions are used only to choose the instructions and the response format. They are not included in the released evaluation set or in the reported scores.

The prompt is selected according to its behavior across several model configurations. We consider whether the response contains valid JSON, whether it follows the required schema, and whether its final answer and trace can be evaluated correctly. We also compare final-answer accuracy, exact trace accuracy, trace completeness, graph-valid exploration, and \texttt{NO\_RESPONSE}. This prevents the prompt from being chosen only because it improves one model or one metric. After this calibration, the instructions, examples, and schema are frozen.

The final prompt contains the generated Java class, the source and target methods, the definition of the task family, and one positive and one negative example. In both families, the model must return the same structure:
\begin{verbatim}
{
"final_answer": true | false,
"trace": [
  "methodName0", "methodName1", ...
]
}
\end{verbatim}
The difference between the families is therefore not the output format. It is the definition of which visible calls are executable.

The parser applies the same rules to every response. It searches for valid JSON objects and keeps the last object that can be parsed. A response is marked as \texttt{NO\_RESPONSE} when no valid object is found, when one of the required fields is missing, or when \texttt{final\_answer} cannot be converted into a Boolean value.

Method names are normalized conservatively. A predicted name must match a method declared in the generated class under the frozen normalization rules. The parser does not correct spelling, infer a missing method, reorder the trace, or complete it. Its role is to extract the response, not to repair the model's reasoning. The parsed record contains the normalized answer and trace, the parsing status, and diagnostics about names, transitions, and stopping behavior.

\subsection{Measuring Model Behavior}
\label{subsec:scoring}
\label{subsec:statistical-analysis}

The evaluator compares the parsed record with the oracle. We use six metrics because a single score cannot represent all the possible outcomes of the task.

\input{tables/metrics}

All main results use strict scoring. A \texttt{NO\_RESPONSE} is counted as incorrect for every accuracy-based metric and is also reported separately. Exact trace accuracy requires the complete predicted trace to be equal to the canonical trace. Trace completeness gives partial credit when oracle methods appear in the correct order. Graph-valid exploration checks whether transitions are executable and whether the trace stops according to the query polarity. Syntactic-call bias records whether a condition-aware trace follows a visible call whose condition is false. Non-strict variants, if reported, are placed in the appendix and explicitly conditioned on a parsable response.

Several questions can come from the same Java class. Their errors may therefore be related. To account for this dependency, we compute confidence intervals with a non-parametric class-cluster bootstrap. Each repetition samples classes with replacement and keeps all their questions. Unless stated otherwise, we use \texttt{[N\_BOOTSTRAP]} repetitions and report two-sided 95\% percentile intervals.

When two configurations are evaluated on the same instances, we compare them with paired class-cluster bootstrap intervals. Comparisons between the two task families remain unpaired unless matched versions of the same program are available. For multiple confirmatory pairwise tests, we apply the Holm--Bonferroni correction and report effect sizes together with significance results.

The three research questions use the same evaluated responses but examine them at different levels. \researchq{1} separates the scores according to trace length, class size, polarity, and generated conditions. \researchq{2} compares the complete model configurations and, when available, their verified reasoning budgets. \researchq{3} uses the oracle graph to classify incomplete traces, invalid transitions, answer--trace inconsistencies, and syntactic-call bias. Examples are selected only after the aggregate errors have been counted.

An analysis introduced after the protocol has been frozen is marked as exploratory. We do not remove a class, question, response, or factor configuration after observing model performance unless the exclusion rule was defined before the final run.

\subsection{Reproducing the Experiment}
\label{subsec:artifact-support}

The anonymized artifact follows the same four steps as the experiment. It contains the generated dataset or the frozen generation configuration, the Java programs and oracle metadata, the prompts and inference manifests, the parser, the evaluator, and the statistical-analysis scripts. Raw and parsed outputs are also included when their licenses, storage requirements, and double-anonymous review allow them to be shared. When an output cannot be released, the artifact explains why and provides the metadata needed to generate it again.

The review artifact is available at \texttt{[ARTIFACT\_URL]}.
