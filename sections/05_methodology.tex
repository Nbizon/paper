\section{Experimental Methodology}
\label{sec:methodology}

This section specifies the protocol used to evaluate model configurations on the frozen \benchmark release. The benchmark construction, oracle semantics, canonical-trace convention, and research questions are defined in Sections~\ref{sec:benchmark-design} and~\ref{sec:research-questions}; we do not restate them here. Instead, we describe the operational choices that determine how instances are selected, prompted, served to models, parsed, scored, and analyzed. All choices in this section are fixed before the final evaluation run. No prompt template, parser rule, metric definition, model setting, or statistical procedure is changed after inspecting final test outputs.

Release-specific constants that depend on the stabilized rerun are shown as bracketed placeholders and are instantiated in the camera-ready artifact.

\subsection{Evaluation Set}
\label{subsec:evaluation-set}

The evaluation set contains \texttt{[N\_INSTANCES]} validated source--target queries drawn from \texttt{[N\_CLASSES]} generated Java classes. It covers the context-size grid \texttt{[CONTEXT\_SIZES]}, the signed canonical trace-length range \texttt{[TRACE\_LENGTH\_RANGE]}, the task families \texttt{[TASK\_FAMILIES]}, the guard settings \texttt{[GUARD\_SETTINGS]}, the code-surface settings \texttt{[PARAMETER\_SETTINGS]}, and the random seeds \texttt{[RANDOM\_SEEDS]}. The realized positive/negative balance is \texttt{[POSITIVE\_NEGATIVE\_BALANCE]}.

Instances are retained only if the generator and validator agree on compilation, method inventory, oracle label, canonical trace, executable graph metadata, and guard metadata when applicable. For each requested trace length, positive and negative queries are selected in balanced pairs whenever both labels are available. When a factor cell cannot provide both polarities, the realized counts are reported and that cell is excluded from analyses requiring exact balance.

Each generated class is stored as a self-contained experiment directory containing the Java source, prompt context, sampled queries, oracle metadata, method list, graph metadata, guard metadata, and generation configuration. The inference runner consumes this directory structure unchanged. Downstream parsing and scoring operate only on stored model outputs and frozen oracle files.

\subsection{Experimental Factors}
\label{subsec:experimental-factors}

The primary factors are task family, signed canonical trace length, generated class size, query polarity, and model configuration. For condition-aware instances, we additionally analyze guard-specific metadata: the number of generated guards, the number of syntactically visible but non-executable calls, and whether a predicted transition follows such a disabled call.

Code-surface features such as comments, local variables, method parameters, loops, and declaration order are treated as primary factors only when they are enabled in the frozen evaluation configuration. Otherwise, they are recorded for descriptive analysis but are not used to support confirmatory claims.

When comparing task families, we use matched factor distributions whenever the frozen release supports them. Unless the release explicitly pairs the same abstract query across unguarded and condition-aware variants, family-level comparisons are treated as unpaired.

\subsection{Model Configurations}
\label{subsec:model-configurations}

We evaluate deployed model configurations rather than checkpoint names alone. A configuration consists of the checkpoint identifier, model revision when available, serving backend, backend version, precision, tensor-parallel setting, maximum context length, chat template, decoding parameters, output-token budget, stop criteria, batching or concurrency setting, and any exposed reasoning-budget control.

\input{tables/models}

All configurations are served locally through an OpenAI-compatible interface. For each model--instance pair, the runner submits one request using the frozen prompt template and stores the raw response together with request metadata, response metadata, wall-clock status, decoding parameters, and failure status. Failed requests are retried according to the fixed policy \texttt{[RETRY\_POLICY]}. If all retries fail, the instance remains in the denominator and is scored as \texttt{NO\_RESPONSE}.

Run manifests record the hardware configuration, backend invocation, precision, tensor-parallel size, context limit, output budget, concurrency setting, random seed when supported, memory-related settings, and full command-line arguments. Decoding is deterministic whenever the backend supports deterministic execution. If deterministic execution is not guaranteed by the backend, this limitation is recorded in the manifest.

Reasoning-budget analyses are performed only for configurations where the serving stack exposes a verifiable budget control and the run metadata confirms that the requested control was accepted. Budget results are therefore interpreted as properties of specific deployed configurations, not of checkpoint families in general.

\subsection{Prompt Calibration and Final Prompting}
\label{subsec:prompt-calibration}

Prompt calibration is performed on a separate pilot set generated with disjoint random seeds and excluded from the final benchmark release. The pilot set is used only to select the prompt template and parser-facing output schema. No pilot instance or output contributes to the reported evaluation.

Candidate prompts are compared across multiple model configurations using a fixed multi-criteria rule: JSON extractability, schema compliance, final-answer accuracy, exact trace accuracy, trace completeness, graph-valid exploration, and \texttt{NO\_RESPONSE} rate. The selected prompt is the variant with the best overall trade-off under this rule, not the prompt that maximizes one metric for one model. After selection, the prompt text, examples, schema, and family-specific wording are frozen.

The final prompt contains the task instruction, the generated Java class, the queried source and target methods, the required JSON schema, and illustrative positive and negative examples. Both task families use the same schema:
\begin{verbatim}
{
"final\_answer": true | false,
"trace": ["methodName0", "methodName1", ...]
}
\end{verbatim}
Family-specific wording is limited to the reachability semantics. The trace field is always evaluated, including when the Boolean answer is correct.

\subsection{Parsing and Normalization}
\label{subsec:parsing}

Parsing is deterministic and model-agnostic. The parser searches each raw response for valid JSON objects and selects the final parsable object. An output is marked as \texttt{NO\_RESPONSE} if no valid JSON object is found, if a required field is missing, or if \texttt{final\_answer} cannot be normalized to a Boolean value.

Trace normalization is conservative. The parser accepts exact method names under the frozen normalization rules and rejects ambiguous repairs. It does not invent method names, correct misspellings, infer omitted methods, reorder traces, replace aliases, or complete partial paths. A predicted method is valid only if it matches a method in the generated class. This policy prevents model-specific or evaluator-specific repair from influencing the results.

For each output, the parser emits a structured record containing the normalized answer, normalized trace, parsing status, method-name validity diagnostics, transition diagnostics, and stop-condition diagnostics. The scoring scripts consume only these structured records and the frozen oracle metadata.

\subsection{Scoring}
\label{subsec:scoring}

The main metrics are final-answer accuracy, exact canonical trace accuracy, trace completeness, graph-valid exploration, syntactic-call bias, and \texttt{NO\_RESPONSE} rate.

\input{tables/metrics}

All main accuracy-like metrics use strict scoring: \texttt{NO\_RESPONSE} counts as incorrect and is also reported separately. Exact trace accuracy requires exact equality with the oracle trace. Trace completeness gives partial ordered credit for recovering the oracle trace from the queried source. Graph-valid exploration checks predicted transitions against the executable graph and verifies the family-specific stopping condition. Syntactic-call bias is computed only for condition-aware instances and records whether a predicted transition follows a visible call disabled by the generated guard outcomes.

Non-strict scores, if reported, are placed in the appendix and labeled as conditional on extractable responses.

\subsection{Statistical Analysis}
\label{subsec:statistical-analysis}

Results are reported by task family, model configuration, signed canonical trace length, generated class size, query polarity, and guard metadata when applicable. Because multiple queries may originate from the same generated class, we do not assume query-level independence.

Uncertainty is estimated with a non-parametric class-cluster bootstrap: each bootstrap replicate samples generated classes with replacement and retains all evaluated queries belonging to each sampled class. Unless otherwise stated, we report two-sided 95% percentile intervals over \texttt{[N\_BOOTSTRAP]} bootstrap replicates. The same procedure is used for proportions and bounded trace-completeness scores.

For model configurations evaluated on the same frozen instances, pairwise differences are estimated with paired class-clustered bootstrap intervals. For unpaired family comparisons, we use unpaired class-clustered intervals and avoid paired tests. When multiple confirmatory pairwise comparisons are reported, $p$-values are adjusted with the Holm--Bonferroni procedure. Effect sizes are reported alongside significance tests.

Breakdowns not specified in the frozen analysis plan are labeled exploratory. No instance, class, factor cell, or model output is removed after observing model performance unless the exclusion rule was fixed before the final run.

\subsection{Research-Question Mapping}
\label{subsec:rq-mapping}

For \researchq{1}, we report final-answer, trace-level, graph-validity, and invalid-output metrics across structural factors. The main comparisons focus on how performance changes with canonical trace length, class size, polarity, and condition-aware guards.

For \researchq{2}, we compare deployed model configurations as evaluated, including serving mode and verified reasoning-budget controls when available. Budget curves are reported only for configurations with confirmed support for the requested control. For such configurations, we report the smallest requested budget that reaches at least 95% of the maximum observed final-answer accuracy, together with trace metrics and \texttt{NO\_RESPONSE} rates.

For \researchq{3}, we analyze parsed traces using deterministic checks over oracle metadata. The analysis covers answer--trace consistency, graph-valid exploration, recurrent trace-error families, and syntactic-call bias. Representative examples are selected after aggregate counts are computed and are used only to illustrate already quantified patterns.

\subsection{Artifact Support}
\label{subsec:artifact-support}

The anonymized artifact contains the material needed to reproduce the evaluation pipeline: frozen benchmark data or generation configuration, generated Java programs, oracle metadata, prompt templates, inference manifests, parser implementation, metric implementation, statistical-analysis scripts, and dashboard materials when used. Raw and parsed model outputs are included when permitted by model licenses, storage constraints, and double-anonymous review requirements. Any unavailable outputs are documented with the reason for exclusion and the metadata needed to regenerate them.
