\section{Experimental Methodology}
\label{sec:methodology}

This section specifies the experimental protocol used to evaluate LLMs on the frozen \benchmark release. Sections~\ref{sec:benchmark-design} and~\ref{sec:research-questions} define the benchmark instances, oracle graphs, canonical traces, and research questions; the present section fixes how those instances are retained, prompted, served to models, parsed, scored, and analyzed. At this stage, the protocol is fixed but some release-specific constants remain placeholders until the stabilized rerun is completed. The final submission will replace these placeholders with the frozen dataset configuration, model configurations, inference settings, and statistical procedures used to produce the reported results.

\subsection{Evaluation Dataset}

The evaluation unit is a validated source--target query over a generated Java class. Each retained query has an oracle reachability label, an oracle canonical trace, and metadata for the controlled factors used in the analysis. Both unguarded reachability and condition-aware reachability are primary evaluation families.

The stabilized release records the number of generated classes, number of queries, context-size grid, signed canonical trace-length range, positive/negative balance, guard settings, parameter settings, and random seeds. These release constants are denoted by placeholders such as \texttt{[N\_CLASSES]}, \texttt{[N\_INSTANCES]}, \texttt{[CONTEXT\_SIZES]}, and \texttt{[TRACE\_LENGTH\_RANGE]} until the rerun is complete. The generator materializes each retained context as a directory containing the generated Java class, prompt context, reachability questions, oracle chains, method names, and configuration metadata. For each requested trace length, positive and negative queries are selected in balanced pairs when both are available.

\subsection{Experimental Factors}

The primary factors are task family, signed canonical trace length, generated class size, query polarity, and model configuration. Unguarded and condition-aware instances are treated as equally important primary settings rather than as a main task and appendix variant. For condition-aware instances, we additionally analyze guard-related metadata, including the number of generated guards and whether predicted transitions follow syntactically visible calls that are excluded from the executable graph by generated guard outcomes.

Comments, local variables, method parameters, loops, and declaration order are code-surface metadata. They are not primary factors unless they are part of the frozen evaluation configuration. Family comparisons use matched factor distributions when possible. Unless the final release pairs the same abstract graph and query across both families, we do not treat unguarded and condition-aware comparisons as paired observations.

\subsection{Model Configurations and Inference Protocol}

We evaluate LLMs at the level of model configurations, not checkpoint names alone. A model configuration includes the checkpoint identifier, serving backend, precision, tensor parallelism, context limit, decoding parameters, output budget, and any exposed reasoning-budget control. This distinction is necessary because the same checkpoint can behave differently under different deployment and decoding settings.

All configurations are served locally through an OpenAI-compatible inference interface. The inference runner reads the generated experiment directories, applies the frozen prompt template, sends each query to the configured model, and stores structured result files for later parsing and scoring. The finalized artifact records backend version, hardware setting, precision, tensor-parallel size, context limit, decoding parameters, concurrency, output budget, and memory settings as reproducibility metadata.

Reasoning-budget controls are recorded as configuration metadata when the serving stack exposes them. Budget-specific analyses are deferred to the model and inference results for \researchq{2}, and are reported only for configurations where the requested control is verified by the serving setup.

\subsection{Prompting and Output Parsing}

The final prompt is example-based. It contains task instructions, the generated Java class, the queried caller and target methods, the required JSON output schema, and illustrative positive and negative examples. The examples make both the output format and the canonical execution-oriented trace convention explicit: the trace follows executable calls in code order from the queried caller until the target is reached or the source-reachable region is exhausted. The trace follows this execution-order convention rather than a path-minimization convention.

Before the final evaluation, we calibrated several prompt variants on a separate pilot set excluded from the reported benchmark release. Prompt selection used a multi-criteria comparison across multiple model configurations, including schema compliance, extractable JSON rate, final-answer accuracy, canonical trace accuracy, trace completeness, and graph-valid exploration. The selected template was the one that provided the best overall trade-off across these criteria rather than optimizing a single metric or a single model configuration. After calibration, the prompt templates were frozen and used unchanged for all reported runs.

Family-specific wording is limited to the task distinction. Unguarded prompts ask models to follow executable method calls from the queried caller. Condition-aware prompts additionally ask models to account for generated values and guards when deciding whether visible calls execute. In both families, the required output contains a normalized reachability decision field and a trace field.

Output parsing is deterministic. The parser extracts the final valid JSON object when extra text surrounds the answer. Invalid or non-extractable outputs are marked \texttt{NO\_RESPONSE}. Trace normalization is deliberately limited: it may handle unambiguous formatting variants, but it must not invent method names or repair semantically invalid traces.

\subsection{Scoring and Analysis Plan}

Outputs are scored against the oracle reachability label, oracle canonical trace, and validated executable graph. The primary scores are final-answer accuracy, canonical trace accuracy, trace completeness, graph-valid exploration, syntactic-call bias, and \texttt{NO\_RESPONSE} rate.

Final-answer accuracy measures the normalized reachability decision only. Canonical trace accuracy requires exact agreement with the oracle trace. Trace completeness measures ordered recovery of the oracle trace from the queried source. Graph-valid exploration checks whether predicted transitions follow executable edges and whether the trace satisfies the family-specific stopping condition. Syntactic-call bias is computed only for condition-aware instances by detecting predicted transitions that follow visible calls excluded from the executable graph by generated guards.

All main accuracy-like scores use strict scoring: \texttt{NO\_RESPONSE} counts as incorrect and is also reported separately. We report scores by task family, model configuration, signed canonical trace length, class size, and query polarity. Guard-specific analyses are reported for condition-aware instances.

The final analysis reports uncertainty for primary proportions and bounded trace-completeness scores using the frozen interval procedures \texttt{[CI\_METHOD]} and \texttt{[TRACE\_CI\_METHOD]}. When multiple queries originate from the same generated class, the analysis accounts for within-class dependence using the frozen analysis model \texttt{[DEPENDENCE\_MODEL]}. Model-by-factor breakdowns outside the main analysis plan are treated as exploratory.

\subsection{Reproducibility}

The anonymized artifact supports reproduction of the experiment. It includes the frozen dataset or generation configuration, generated Java programs, oracle metadata, prompt templates, inference configurations, parser and metric implementations, statistical-analysis scripts, and dashboard or analysis materials when used. Raw or parsed model outputs are included when shareable. Any restrictions due to model licenses or storage constraints are recorded in the artifact documentation, together with the review artifact location \texttt{[ARTIFACT\_URL]}.
