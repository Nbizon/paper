The benchmark instance is a tuple:
\[
(\text{Java class}, \text{source}, \text{target}, \text{family}, y, \tau, m),
\]
where $y$ is the oracle final answer, $\tau$ is the canonical execution-oriented trace, and $m$ is metadata recording generation factors such as context size, signed canonical distance, label polarity, code-surface configuration, and task family.
The label $y$ is the Boolean reachability label: $y=\true$ when the target method is reachable from the source method in the executable call graph, and $y=\false$ otherwise. The trace $\tau$ is evaluated separately from this label.

\subsection{Experimental Factors}

The empirical study focuses on four primary factors:
\begin{itemize}[leftmargin=*]
    \item \textbf{Canonical execution distance:} the number of canonical exploration steps required to reach the target for positive queries, or to exhaust the reachable region for negative queries.
    \item \textbf{Class size:} the number of generated methods in the Java class, operationalized through planned context sizes 100, 250, and 500. \TODO{Confirm that the frozen datasets use exactly context sizes 100, 250, and 500.}
    \item \textbf{Query polarity:} whether the target is reachable or unreachable from the source. The generator samples balanced positive and negative questions at each retained distance.
    \item \textbf{Condition-aware guards:} the number and placement of generated \texttt{if} statements that may contain visible but non-executable calls.
\end{itemize}
Other surface factors, including comments, local variables, parameters, loops, and declaration order, are retained as metadata for secondary analyses. In the inspected tree configuration, loops do not contain generated reachability calls.

\subsection{Canonical Trace and Signed Distance}

The evaluator uses the canonical trace defined in \secref{sec:benchmark-design}. Listing~\ref{lst:canonical-trace} summarizes the generator convention inspected for this revision.

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize,frame=single,caption={Canonical execution-oriented trace used by the generator.},label={lst:canonical-trace}]
CanonicalTrace(src, tgt, maxD):
    trace = ExecPrefix(src, maxD + 1)
    if tgt at index i:
        return trace[0:i+1], +i
    if subtree complete:
        return trace, -(len(trace)-1)
    otherwise:
        skip negative query
\end{lstlisting}

In the inspected tree generator, stored signed distance is the target position for positive queries and the explored reachable-region size minus one for negative queries.

\subsection{Prompting Protocol}

The prompt states the task and JSON schema without naming a particular traversal algorithm. The unguarded prompt does not mention condition evaluation; the condition-aware prompt tells the model to use generated values and guards when deciding whether a visible call executes. In both families, the trace is the explored call sequence in code order, not a shortest path unless the oracle trace has that form.

\subsection{Output Parsing}

The parser extracts the last parsable JSON object from each output. Extra prose is ignored if at least one object can be decoded; when several objects appear, the final parsable one is used. A case is counted as \texttt{NO\_RESPONSE} when no valid object provides an extractable \texttt{final\_answer}, or when the output is truncated before that field appears. The trace field is normalized from a JSON list or common string separators when possible.

The main paper uses strict scores: \texttt{NO\_RESPONSE} counts as incorrect for accuracy-like metrics. We do not plan conditional appendix scores that exclude \texttt{NO\_RESPONSE}.

\subsection{Baselines and Sanity Checks}

The evaluated LLMs are the primary systems under test rather than baselines in the classical sense. Simple non-LLM baselines help calibrate task difficulty and interpret failures.

\begin{itemize}[leftmargin=*]
    \item \textbf{Random-label baseline.} This baseline predicts a reachability label according to the empirical label distribution and emits an empty or minimal trace. It calibrates final-answer accuracy under label balance.
    \item \textbf{Syntactic-call baseline.} This baseline treats every syntactically visible method call as executable. It is expected to perform well on unguarded instances but to fail on condition-aware instances when false-branch calls are visible but non-executable.
    \item \textbf{Shortest-executable-path baseline.} Given the executable call graph, this baseline emits the shortest path from source to target for positive queries and a reachability label for negative queries. It separates semantic reachability from the stricter canonical exploration convention.
    \item \textbf{Oracle-traversal sanity check.} This deterministic check runs the same canonical traversal used by the oracle over the validated executable call graph. It should achieve perfect scores and serves as an implementation sanity check rather than a competing method.
\end{itemize}

\subsection{Why Evaluate Canonical Traces?}

The canonical trace is stricter than a reachability path. A shortest path can show that the target is reachable, but it does not test the requested execution-oriented exploration convention. We therefore report exact trace accuracy, trace completeness, and graph-valid exploration separately, distinguishing semantic reachability, valid transitions, and strict oracle-order agreement.

\subsection{Oracle Validation}

Given the validated executable call graph, the oracle-traversal sanity check solves each query by construction. The validation pipeline checks compilation, materialized call consistency, reachability labels, canonical traces, and condition evaluation for guarded calls.
