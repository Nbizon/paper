\section{Methodology}
\label{sec:methodology}

\subsection{Experimental Scope}

The reported empirical results use the control-flow family of \benchmark. Each instance contains a generated Java class, a source-target reachability question, an oracle label, and an oracle trace. To keep model comparisons balanced, we report the common slice shared by all evaluated models: contexts of 100, 250, and 500 methods; depths 1--25; and requested reasoning budgets of 512, 1024, 2048, 4096, 8192, and 16,384 tokens. Contexts 750 and 1000 are generated by the benchmark but excluded from the headline comparison when they are not available for every model.

\subsection{Models and Inference}

We evaluate three reasoning-capable open-weight models through a vLLM OpenAI-compatible serving stack. Each model receives the same generated Java program, the same natural-language question, and the same output schema. The decoding setup requests a reasoning budget and an answer budget; for models that support a thinking-token parameter, the requested reasoning budget is forwarded through the serving interface. We use deterministic or near-deterministic decoding for the benchmark runs so that performance differences primarily reflect the model, prompt, program instance, and requested budget rather than sampling variance.

\subsection{Metrics}

The evaluator parses the model response into a final answer and a trace. The final answer is scored as a Boolean reachability decision. The chain and trace metrics compare the emitted sequence against the oracle path and therefore test whether the model reconstructed the program structure, not only whether it guessed the label.

We additionally compute a tokenizer-counted emitted-reasoning proxy. For each response, the analysis extracts the visible reasoning text between the \texttt{R:} and \texttt{A:} blocks and tokenizes it with the corresponding local model tokenizer. This value is useful for saturation analysis, but it is not the same as a runtime counter for internally consumed reasoning tokens. We therefore report it as emitted reasoning length, not as true consumed reasoning budget.

\subsection{Aggregation and Analysis}

All headline metrics are weighted over the common evaluation slice. We aggregate by model, context size, depth, requested budget, and code-level factors. For \researchq{1}, we compare performance across requested budgets and compute marginal gains between consecutive budget levels. For \researchq{2}, we compare final-answer metrics with chain and trace metrics, then group residual errors into interpretable trace families such as premature termination, alternative branch, invalid transition, over-exploration, and wrong ordering.

The data-flow family uses the same aggregation plan. Its primary trace unit is a value-dependency path rather than a method-call path. This paper describes the design and planned analysis for that family, while the quantified results reported below are the completed control-flow evidence.
