\section{Conclusion}
\label{sec:conclusion}

Existing software-engineering benchmarks mainly show whether an LLM completes a task. \benchmark was introduced to study one of the capabilities that can contribute to this result: following executable calls between methods. The benchmark generates the call graph before the Java program. It therefore knows the expected reachability answer and the sequence of methods that must be explored.

This construction makes two types of analysis possible. First, the generator can vary trace length, class size, polarity, and generated conditions while keeping the task unchanged. Second, the oracle can compare the final answer with the returned trace. A correct answer can therefore be separated from a trace that skips methods, follows an invalid call, or treats a disabled call as executable.

The objective of \benchmark is not to replace program-analysis tools or realistic repository benchmarks. Program-analysis tools remain the appropriate solution for computing reachability in real software, while repository benchmarks measure whether an LLM can complete a full developer task. \benchmark provides a complementary diagnostic setting. It makes it possible to connect model errors with controlled properties of a program and to measure behaviors that are hidden by the final answer alone.
